CH 01왜 "순서"를 읽어야 하나#

리뷰 한 줄은 단어가 일렬로 놓인 시퀀스다. "not good"과 "good"은 같은 단어 good을 품지만 순서·문맥이 의미를 뒤집는다. 그래서 단어 가방(BoW)처럼 순서를 버리는 방식 대신, 앞 단어의 정보를 은닉 상태(Hidden State)에 담아 다음 시점으로 흘려보내는 RNN 계열이 자연스러운 출발점이 된다.

의문강의를 들으며 막혔던 지점. "RNN은 길어지면 앞을 잊는다"는데, 그 '잊음'이 학습할 때 미분값이 사라지는 기울기 소실과 같은 말인가, 다른 말인가?

정리하면 두 가지를 구분해야 했다. 순방향(Forward)에서 입력이 tanh·가중치를 거치며 반복 곱해져 앞쪽 단어의 특징 자체가 희석되는 것은 정보 소실(Information Loss) / 장기 의존성 문제다 — 데이터가 날아간다. 반면 역전파(Backprop)에서 tanh 미분값(최대 1)이 시점만큼 연쇄로 곱해져 0에 수렴하는 것은 기울기 소실(Vanishing Gradient)이다 — 학습 신호가 날아간다. 둘은 원인-결과로 얽혀 있지만 일어나는 시점과 대상이 다르다.

배운 점LSTM이 RNN보다 초기 정보를 오래 버티는 핵심은 셀 상태(Cell State)다. 일반 RNN은 과거 정보에 가중치를 곱하고 tanh를 씌워 넘기지만(곱셈 → 소실), LSTM의 셀 상태 라인은 망각 게이트를 통해 과거 정보를 더해서(+) 흘려보낸다. 미분 시 곱셈은 쉽게 사라지지만 덧셈은 기울기를 그대로 보존하기 때문에, 일종의 '메모리 고속도로'처럼 작동한다.

오늘 짠 모델이 단방향 1층 LSTM인 이유도 여기 있다. 양방향·다층으로 키우기 전에, "순서를 읽어 마지막 은닉 상태 하나로 문장을 요약한다"는 가장 기본 구조부터 손에 익히는 게 목표였다.

CH 02LSTM 감성분류기 한 채 짓기#

구조는 단순하다. 단어 인덱스 → 임베딩 벡터 → LSTM으로 순서대로 읽기 → 마지막 은닉 상태 → 선형층으로 2개 클래스 점수. 설정값은 max_len 200, batch 64, embedding/hidden 128, num_layers 1, dropout 0.3, lr 1e-3, max_epochs 3으로 잡았다.

self.embedding = nn.Embedding(
    num_embeddings=vocab_size,
    embedding_dim=embedding_dim,
    padding_idx=pad_index,   # <pad> 토큰(0)은 학습에 거의 영향 안 주게
)
self.lstm = nn.LSTM(
    input_size=embedding_dim,
    hidden_size=hidden_dim,
    num_layers=num_layers,
    batch_first=True,        # 입력 형태 (배치, 문장길이, 임베딩차원)
    dropout=dropout if num_layers > 1 else 0.0,
    bidirectional=False,
)
self.dropout = nn.Dropout(dropout)
self.classifier = nn.Linear(hidden_dim, 2)   # 부정/긍정 2개 클래스
self.loss_fn = nn.CrossEntropyLoss()

forward에서 결정적인 한 줄은 어떤 출력을 쓸 것인가였다. LSTM은 모든 시점의 출력과 마지막 은닉 상태를 함께 돌려준다. 분류에서는 문장 전체를 다 읽은 뒤의 마지막 은닉 상태 하나면 충분하다.

embedded = self.embedding(input_ids)        # (배치, 문장길이, 임베딩차원)
output, (hidden, cell) = self.lstm(embedded)
sentence_vector = hidden[-1]                 # 마지막 층의 마지막 은닉 상태
sentence_vector = self.dropout(sentence_vector)
logits = self.classifier(sentence_vector)   # (배치, 2)  — softmax 없이 logits 그대로
return logits

설계 메모PROBLEM_REPORT에 적힌 초기 버전은 LSTM 전 시점 출력에 선형층을 걸고 x.sum(dim=1)으로 모든 위치 점수를 합산하는 비표준 방식이었다. 표준은 hidden[-1] 한 줄. RNN/LSTM 분류에서는 마지막 은닉 상태만 쓴다는 기본기를 코드로 되짚었다.

전처리도 같이 손봤다. 짧은 리뷰는 패딩, 긴 리뷰는 자르기. 강의에서 본 한 줄짜리 슬라이싱 트릭이 떠올라 직접 비교해봤는데, (encoded + [PAD]*max_len)[:max_len]처럼 줄여도 if/else로 분기한 결과와 출력 벡터가 100% 일치한다. 이 코드에서는 가독성을 위해 분기형을 택했다.

token_ids = token_ids[:max_len]
if len(token_ids) < max_len:
    token_ids = token_ids + [word_to_index["<pad>"]] * (max_len - len(token_ids))
return torch.tensor(token_ids, dtype=torch.long)  # Embedding은 long을 요구

CH 03첫 번째 벽 — WinError 127#

초기 코드는 데이터 로딩을 torchtext.legacy에 맡기고 있었다. Field, BucketIterator, IMDB 데이터셋까지 한 번에 끌어오는 편한 길이었는데, 실행하자마자 임포트 단계에서 죽었다.

FAILURE학습은 시작도 못 했다. torchtext를 임포트하는 순간 C++ 확장 로딩이 실패하며 프로세스가 중단됐다.

from torchtext.legacy.data import Field, BucketIterator
from torchtext.legacy.datasets import IMDB

OSError: [WinError 127] 지정된 프로시저를 찾을 수 없습니다.
  (libtorchtext.pyd 로드 실패)

CLUEWinError 127 "지정된 프로시저를 찾을 수 없습니다"는 DLL/pyd가 기대한 심볼을 못 찾을 때 나는 전형적 증상. libtorchtext.pyd가 설치된 torch 2.x의 ABI와 맞물리지 못한 것 — 즉 torchtext와 torch의 버전 호환성 불일치였다. torchtext.legacy 자체도 구버전 API라 최신 환경에서 사실상 폐기 수순이다.

해결은 의외로 라이브러리를 빼는 쪽이었다. torchtext를 통째로 제거하고(pip uninstall -y torchtext), IMDB aclImdb 폴더의 txt 파일을 직접 읽는 파일 기반 로더를 손으로 구현했다. neg=0, pos=1로 라벨을 붙이고 Counter로 vocabulary를 만든다. 의존성을 줄이니 배치 형태(batch_size, seq_len)도 내가 100% 통제하게 됐다.

def read_imdb_split(dataset_path, split):
    samples = []
    label_map = {"neg": 0, "pos": 1}
    for label_name, label_id in label_map.items():
        review_dir = dataset_path / split / label_name
        for file_path in sorted(review_dir.glob("*.txt")):
            text = file_path.read_text(encoding="utf-8", errors="ignore")
            samples.append((text, label_id))
    random.shuffle(samples)
    return samples

해결"편한 고수준 래퍼가 환경에서 안 돌면, 한 단계 내려가 직접 짠다." torchtext가 빠지자 오히려 데이터 흐름이 투명해졌다. 호환성 지옥에서 빠져나오는 가장 빠른 길이 의존성 추가가 아니라 제거일 때가 있다.

CH 04두 번째 벽 — 출력이 3차원?#

로더를 고치고 다시 돌리니, 이번엔 모델 쪽 차원이 어긋나 있었다. 분류기 출력을 output_size=3으로 잡아둔 것이다. IMDB는 긍정/부정 단 2개 클래스인데.

FAILURE출력 3차원 + 라벨 2종(0/1). 손실·메트릭 계산에서 차원이 어긋난다. 게다가 정확도 메트릭도 task="multiclass", num_classes=3으로 연쇄로 잘못 걸려 있었다.

CLUE일반적인 다중분류를 무심코 가정한 흔적이었다. IMDB 감성분류는 이진 태스크다. 출력 차원, 손실 함수, 메트릭의 task 타입 — 이 셋이 같은 가정 위에 서 있어야 한다.

# 잘못된 가정
def __init__(self, ..., output_size=3): ...
self.train_accuracy = Accuracy(task="multiclass", num_classes=3)

# 수정 — 긍/부정 2클래스로 통일
self.classifier = nn.Linear(hidden_dim, 2)
self.train_acc = BinaryAccuracy()   # torchmetrics, task="binary"

여기에 PyTorch Lightning의 자잘한 함정도 하나 걸렸다. devices=None으로 두면 CPU에서 "devices selected with CPUAccelerator should be an int > 0" 에러가 난다. GPU든 CPU든 devices=1로 고정하는 게 안전했다.

trainer = pl.Trainer(
    max_epochs=config.max_epochs,
    accelerator="gpu" if torch.cuda.is_available() else "cpu",
    devices=1,                 # CPU/GPU 모두 1로 고정
    enable_checkpointing=False,
)

배운 점모델을 "돌아가게 만드는 일"의 정체는 결국 차원과 가정의 일관성 점검이었다. 출력 차원 ↔ 손실 함수 ↔ 메트릭 task가 같은 클래스 수를 바라보고 있는지, 그리고 Trainer 파라미터가 디바이스 규칙을 지키는지. 이 두 벽(WinError 127, output_size)을 넘는 게 오늘 작업의 절반이었다. (학습 후 최종 test 정확도 수치는 리포트에 별도 기록이 없어 여기서는 다루지 않는다.)

CH 05다음 길 — Seq2Seq와 어텐션의 예고#

오늘은 "시퀀스 → 하나의 판단"이었다. 그런데 번역·요약·챗봇처럼 시퀀스 → 시퀀스가 필요해지면 구조가 달라진다. Seq2Seq는 입력을 압축하는 인코더와 출력을 생성하는 디코더, 두 개의 RNN 계열 모델을 잇는다. 인코더에 양방향(BiRNN)을 흔히 쓰고, 디코더는 미래 단어를 미리 보면 안 되므로 단방향을 쓴다.

의문강의 중 떠오른 질문. "Seq2Seq라는 게 결국 그냥 BiRNN 인코더 + 단방향 디코더 구조 아닌가? LSTM을 써서 정보 휘발을 줄인 것뿐이고?"

뼈대는 맞다. 다만 거창한 이름이 붙은 건 패러다임이 달랐기 때문이다. 과거 RNN은 입력과 출력을 1:1 실시간으로 매칭해 어순 다른 번역이 불가능했다. Seq2Seq는 "문장을 끝까지 다 듣고(인코더), 생각을 정리한 뒤 처음부터 새로 쓴다(디코더)"는 방식을 제안했다. 정보 휘발은 LSTM의 셀 상태로 일부 막았다.

한계와 다음 주제그래도 한계가 남는다. 아무리 길어도 문장 전체를 고정 크기 컨텍스트 벡터 하나에 구겨 넣어야 하니, 30~40단어를 넘기면 정보가 병목에서 터진다. 이걸 깨려고 "디코더가 매 시점 인코더의 모든 은닉 상태를 직접 돌아보게 하자"는 어텐션(Attention)이 등장하고, RNN을 아예 걷어낸 게 트랜스포머다. 다음 주의 주제 — 오늘은 가볍게 예고만.
