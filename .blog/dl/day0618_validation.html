정확도 한 숫자로 충분한가 — 모델을 어떻게 믿을 것인가

test 정확도 96%라는 한 줄이 나왔다고 모델을 신뢰해도 되는가. 데이터를 train/val/test로 가르는 이유부터, 정확도가 가리는 오류를 혼동행렬·정밀도·재현율·F1·ROC-AUC로 풀어내는 과정, 그리고 같은 평가를 TensorFlow와 PyTorch가 어떻게 다르게 코드로 옮기는지까지 정리한다.

모델 학습은 끝났다고 치자. 그다음 "이 모델 쓸 만한가?"라는 질문에 답하는 게 검증과 평가다. 출발점은 데이터를 어떻게 나누느냐다.

CH 01 왜 데이터를 셋으로 가르나#

모델을 학습시킨 데이터로 그 모델을 평가하면 점수는 항상 후하게 나온다. 시험 문제를 미리 보고 친 시험 점수를 실력이라 부를 수 없는 것과 같다. 그래서 데이터를 역할이 다른 세 덩어리로 나눈다.

역할 분담 Train은 가중치를 학습하는 데, Validation은 학습 중 하이퍼파라미터 튜닝과 조기 종료(Early Stopping) 판단에, Test는 최종 일반화 성능을 단 한 번 측정하기 위해 아껴 두는 데이터다.

핵심은 Test를 학습 과정 어디에도 노출시키지 않는 것이다. Validation을 따로 두는 이유도 여기 있다. 학습을 멈출 시점이나 층 수 같은 결정을 Test로 내리는 순간, Test는 더 이상 "처음 보는 데이터"가 아니게 되고 일반화 성능을 과대평가하게 된다.

핵심 Train으로 배우고, Validation으로 멈출 때를 정하고, Test로 단 한 번 판정한다. 데이터가 적으면 K-Fold 교차검증으로 검증셋을 번갈아 써서 변동성을 줄인다.

개념은 이렇다. 그러면 569개짜리 실제 데이터에서 이 분할이 정확히 몇 개씩으로 떨어지는지 보자.

CH 02 569개를 397/86/86으로#

실습 데이터는 scikit-learn의 Breast Cancer 데이터셋이다. 샘플 569개, 특성 30개, 이진 분류(악성 malignant=0, 양성 benign=1) 문제다. 분할은 두 번에 나눠 한다. 먼저 전체에서 15%를 Test로 떼고, 남은 85%에서 다시 17.65%를 Validation으로 뗀다. 이렇게 하면 대략 70/15/15가 된다.

# 1차: 전체 → (train+val) / test
X_train_val, X_test, y_train_val, y_test = train_test_split(
    X, y, test_size=0.15, random_state=42, stratify=y)

# 2차: (train+val) → train / val
X_train, X_val, y_train, y_val = train_test_split(
    X_train_val, y_train_val, test_size=0.1765, random_state=42, stratify=y_train_val)

print(X_train.shape, X_val.shape, X_test.shape)
print(np.bincount(y_test))

같은 random_state로 재현하면 분할 크기는 다음처럼 떨어진다.

학습 데이터 크기: (397, 30)
검증 데이터 크기: (86, 30)
테스트 데이터 크기: (86, 30)
테스트 클래스 분포 (malignant=0, benign=1): [32 54]

두 가지를 짚어 둘 만하다. 첫째, stratify=y로 원래 클래스 비율(악성 212 : 양성 357)을 각 셋이 그대로 물려받게 했다. 그래서 Test 86개도 악성 32 : 양성 54로 전체와 같은 비율이다. 불균형 데이터에서 이걸 빼먹으면 어떤 셋엔 소수 클래스가 거의 안 들어가는 사고가 난다.

데이터 누수 차단 표준화(StandardScaler)는 반드시 fit_transform을 Train에만 적용하고, Validation·Test에는 transform만 쓴다. Test 통계까지 포함해 fit하면 Test 정보가 전처리 단계로 새어 들어와(data leakage) 평가가 오염된다.

scaler = StandardScaler()
X_train_scaled = scaler.fit_transform(X_train)   # 평균·표준편차는 Train에서만 학습
X_val_scaled   = scaler.transform(X_val)         # 같은 기준으로 변환만
X_test_scaled  = scaler.transform(X_test)
데이터가 깨끗이 갈렸으니, 이제 학습된 모델을 Test로 채점할 차례다. 그런데 채점을 "정확도" 한 숫자로 끝내면 안 되는 이유가 있다.

CH 03 정확도가 가리는 것 — 혼동행렬#

정확도(Accuracy)는 전체 중 맞춘 비율이다. 직관적이지만, 클래스 비율이 한쪽으로 쏠려 있으면 무의미해진다. 암 환자가 1%인 데이터에서 "전부 정상"이라 찍는 모델도 정확도 99%가 나온다. 이 모델은 정작 잡아야 할 환자를 한 명도 못 잡는다. 그래서 "몇 개 맞혔나"가 아니라 "어떻게 틀렸나"를 봐야 한다. 그 도구가 혼동행렬(Confusion Matrix)이다.

혼동행렬은 예측을 네 칸으로 쪼갠다. 실습 코드는 confusion_matrix로 행렬을 만들고 cm.ravel()로 네 값을 풀어 의미를 출력한다.

cm = confusion_matrix(y_true, test_predictions)
tn, fp, fn, tp = cm.ravel()
print("TN: 실제 0을 0으로 맞힌 수")   # True Negative
print("FP: 실제 0을 1로 잘못 예측한 수")  # False Positive
print("FN: 실제 1을 0으로 잘못 예측한 수")  # False Negative
print("TP: 실제 1을 1로 맞힌 수")      # True Positive
구분실제 Positive실제 Negative
예측 PositiveTP (맞게 잡음)FP (헛경보)
예측 NegativeFN (놓침)TN (맞게 거름)

핵심 정확도는 (TP+TN) / 전체일 뿐이라 FP와 FN을 한데 뭉뚱그린다. 하지만 현실에서 "헛경보(FP)"와 "놓침(FN)"의 비용은 전혀 다르다. 혼동행렬은 그 둘을 분리해서 보여 준다.

FP와 FN을 나눠 봤다면, 이제 어느 쪽 오류를 더 줄여야 하는지를 숫자로 표현하는 지표들이 필요하다.

CH 04 정밀도·재현율·F1·ROC-AUC — 문제가 지표를 고른다#

혼동행렬의 네 칸을 조합하면 목적에 맞는 지표가 나온다. 실습은 precision_score, recall_score, f1_score, roc_auc_score를 한 번에 뽑고, classification_report로 클래스별 표까지 출력한다.

지표정의언제 중요한가
정밀도 PrecisionTP / (TP+FP) — Positive라 예측한 것 중 진짜 비율헛경보 비용이 클 때 (스팸 필터: 정상 메일을 스팸으로 버리면 안 됨)
재현율 RecallTP / (TP+FN) — 실제 Positive 중 잡아낸 비율놓치는 비용이 클 때 (암 진단·사기 탐지: 환자를 놓치면 안 됨)
F1-score정밀도와 재현율의 조화 평균둘의 균형이 필요하거나 클래스가 불균형할 때
ROC-AUC임계값을 전 구간 바꿔 가며 본 분류 능력의 총합 (1에 가까울수록 우수)임계값에 독립적인 모델 자체의 분별력을 볼 때

의문 정밀도와 재현율은 한쪽을 올리면 다른 쪽이 내려가는 트레이드오프 관계다. 그렇다면 "어느 걸 봐야 하나"의 답은 모델이 아니라 문제에 있다. 즉 평가지표를 고르는 일은 사실상 문제를 다시 정의하는 일이다.

이 데이터셋은 암 진단이다. 양성 종양을 악성으로 잘못 분류하는 헛경보(FP)보다, 악성 종양을 양성이라 놓치는 것(FN)이 훨씬 위험하다. 그래서 여기서는 재현율을 우선 봐야 한다. 반대로 스팸 필터라면 멀쩡한 메일을 스팸함에 처박는 FP가 더 치명적이라 정밀도를 중시한다. 같은 혼동행렬을 놓고도 어느 칸의 오류를 더 미워할지가 도메인마다 다르다.

주의 이 글에는 학습된 모델의 실제 지표 수치(정확도·혼동행렬 값·F1·ROC-AUC)를 싣지 않았다. 실습 노트북에 셀 출력이 저장되어 있지 않아 재현 가능한 수치만 인용한다는 원칙(분할 크기·클래스 분포는 random_state로 고정되어 재현 가능)에 따른 것이다. 지표 칸은 의미와 선택 기준을 정리한 정의표로 읽으면 된다.

평가의 논리는 프레임워크와 무관하다. 하지만 그 논리를 코드로 옮기는 방식은 TensorFlow와 PyTorch가 사뭇 다르다.

CH 05 같은 평가, 다른 코드#

학습이 끝난 모델을 Test로 평가할 때, 두 프레임워크의 추상화 수준 차이가 그대로 드러난다. TensorFlow/Keras는 model.evaluate() 한 줄이 손실과 정확도를 돌려준다.

# TensorFlow / Keras — 한 줄로 평가
test_loss, test_acc = model.evaluate(X_test_scaled, y_test, verbose=0)
test_probabilities = model.predict(X_test_scaled).ravel()
test_predictions = (test_probabilities >= 0.5).astype(int)

PyTorch는 같은 일을 손으로 한다. 평가 모드 전환(model.eval()), 그래디언트 계산 차단(torch.no_grad()), 로짓에 시그모이드를 씌워 확률화하고 0.5 임계값으로 라벨링하는 단계를 직접 쓴다.

# PyTorch — 평가 절차를 직접 구성
model.eval()
with torch.no_grad():
    test_logits = model(X_test_tensor.to(device))
    test_probabilities = torch.sigmoid(test_logits).cpu().numpy().ravel()
    test_predictions = (test_probabilities >= 0.5).astype(int)

핵심 model.eval()은 Dropout·BatchNorm을 추론 모드로 바꾸고, torch.no_grad()는 평가에 불필요한 그래디언트 그래프를 만들지 않아 메모리·속도를 아낀다. Keras의 evaluate()는 이 둘을 안에서 알아서 처리해 준다. 추상화가 편한 만큼, PyTorch 쪽은 무슨 일이 일어나는지가 코드에 그대로 보인다.

여기서 한 가지 빠뜨리기 쉬운 점은 손실 함수다. PyTorch 실습은 마지막 층에 시그모이드를 두지 않고 로짓을 그대로 내보낸 뒤 BCEWithLogitsLoss를 쓴다(수치 안정성 때문). 그래서 평가 단계에서 확률이 필요할 때 torch.sigmoid()를 직접 한 번 적용해야 한다. Keras는 출력층 활성화를 sigmoid로 두고 binary_crossentropy를 쓰므로 predict()가 곧바로 확률이다. 두 길은 같은 곳에 도착하지만, 확률을 어디서 만드느냐의 책임 소재가 다르다.

정리 평가의 본질 — train/val/test 분리, 누수 차단, 문제에 맞는 지표 선택 — 은 프레임워크를 가리지 않는다. 프레임워크가 정하는 건 그 본질을 몇 줄로 쓰느냐, 그리고 그 줄들이 내부를 얼마나 드러내느냐일 뿐이다.
