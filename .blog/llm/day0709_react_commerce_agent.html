종합 프로젝트 — ReAct 커머스 에이전트 (그동안 배운 모든 것의 통합)

형태소 전처리에서 시작해 임베딩·딥러닝 분류·BERT·트랜스포머·LLM API·프롬프트·Function Calling·RAG까지, 28개의 실습이 서로 다른 폴더에 흩어져 있었다. 오늘의 목표는 그 학습들을 하나의 실행 가능한 FastAPI 앱으로 통합한 결과 — "승승장구몰 AI 커머스 에이전트" — 를 아키텍처 관점에서 되짚는 것이다. 각 주제가 프로젝트의 어느 모듈로 내려앉았는지 매핑하고, 실제 ReAct 루프·도구 등록·라우터 코드로 "두뇌·손발·기억이 어떻게 한 요청 안에서 맞물리는가"를 확인한다.

CH 01왜 통합인가 — 흩어진 실습을 하나로#

통합 프로젝트의 한 줄 정의는 이렇다. "llm_workspace의 28개 LLM/NLP 실습을 하나의 실행 가능한 FastAPI 앱으로 통합". 사용자가 "P0001 재고랑 주문 상태 알려주고, 반품 정책도 요약해줘"라고 하면, 에이전트가 스스로 도구(재고·주문 조회)와 RAG(정책 문서 검색)를 조합해 한 번에 답하는 것 — 이 시나리오가 통합의 목표점이다.

의문부품을 다 만들어 놓긴 했는데, 막상 합치려니 막막했다. 감성분석(BERT)·의도분류(임베딩)·RAG(FAISS)·에이전트 루프는 서로 다른 실행 방식과 상태(가중치 로드, 인덱스 로드, DB 세션)를 갖는다. 이 이질적인 것들을 한 요청 안에서 어떤 순서로, 누가 결정해 부르게 만드나?

답은 결국 에이전트가 오케스트레이터가 되는 구조였다. LLM이 두뇌 역할로 "다음에 어떤 도구를 부를지"를 결정하고, DB 조회·환율·RAG 검색은 모두 도구(tool)로 등록돼 손발이 된다. 감성·의도·추천 같은 ML 모델은 독립 API(/api/nlp/*)로 두되 필요 시 도구화할 수 있게 남겼다. 즉 통합의 뼈대는 "스테이지 10~12에서 배운 Function Calling·Agent Loop·RAG"였고, 나머지 스테이지는 그 위에 재료로 얹혔다.

배운 점통합은 "코드를 한 폴더에 복사-붙여넣기"가 아니었다. 실습마다 있던 하드코딩·폴백·데모모드를 제거하는 작업이 절반이었다(프로젝트 RULE 기준). 예를 들어 KoNLPy의 JAVA_HOME, API 키, 모델명, 가격표, FAISS 경로 — 실습에선 코드에 박혀 있던 값들이 전부 app/core/config.py의 설정으로 올라갔다. "학습용 스크립트"와 "제품 모듈"의 차이는 대부분 설정 분리와 실패 처리에 있었다.

CH 02스테이지 ↔ 모듈 매핑 — 배운 주제가 내려앉은 자리#

가장 궁금했던 것 — 그동안 배운 각 주제가 실제로 어느 파일이 됐나. 공략집 부록 D가 이 매핑을 개념→코드로 정리해 뒀다. 통합 앱은 Phase 0~7로 나눠 흡수했고, 각 Phase가 하나 이상의 스테이지를 담는다.

CH 03아키텍처 계층 — 요청이 지나는 길#

매핑을 파일이 아니라 계층으로 다시 보면 요청이 어떻게 흐르는지가 보인다. FastAPI app/main.py가 진입점에서 라우터를 모으고(include_router), 기동 시 lifespan에서 DB 시딩과 RAG 인덱스 빌드를 1회 수행한다(요청마다가 아니라).

핵심은 도구 계층이 에이전트와 데이터 사이의 유일한 다리라는 점이다. 에이전트는 DB를 직접 쿼리하지 않는다 — 언제나 도구를 통해서만 세계에 접근한다. 이 경계 덕분에 "LLM이 결정하고, 파이썬이 실행한다"는 Function Calling의 원칙(스테이지 10)이 아키텍처 수준에서 지켜진다.

배운 점app/core/config.py의 프로바이더 추상화가 통합의 숨은 축이었다. LLM_PROVIDER 하나로 로컬 Gemma(토큰 0, 빌드/오프라인)·OpenAI·Gemini를 갈아끼운다. 로컬로는 요약·분류·프롬프트 같은 평문 작업 전 과정을 토큰 없이 검증하고, 실제 tool-calling만 실키(또는 로컬 Qwen)로 확인한다. "개발 중엔 공짜로, 검증만 유료로"를 설정 한 줄로 나눈 셈이다.

CH 04ReAct 엔진 — 두뇌·손발·기억이 도는 루프#

통합의 심장은 app/agent/react.py의 수동 ReAct 루프다. 스테이지 11에서 배운 Thought → Action(도구) → Observation → 반복이 그대로 코드가 됐다. 학습용으로 손수 구현해, 모델 없이도 chat_fn을 주입하면 결정론적으로 테스트된다.

def run_react_agent(question, db, chat_fn=None, max_steps=3, system_prompt=None):
    chat_fn = chat_fn or _default_chat_fn
    messages = [
        {"role": "system", "content": system_prompt or DEFAULT_SYSTEM_PROMPT},
        {"role": "user", "content": question},
    ]
    steps, seen = [], set()                       # seen: 중복 호출 차단용 서명 집합

    for step_no in range(1, max_steps + 1):       # 안전장치① max_steps
        messages = _trim(messages)                # 안전장치③ history trimming
        assistant = chat_fn(messages, TOOLS_SCHEMA)
        messages.append(_assistant_to_openai(assistant))

        tool_calls = assistant.get("tool_calls")
        if not tool_calls:                        # 도구 호출이 없으면 = 최종 답변
            return AgentResponse(answer=assistant.get("content") or "",
                                 steps=steps, stopped_by="final_answer")

        for tc in tool_calls:
            sig = _signature(tc["name"], args)    # (도구명+인자) 서명
            if sig in seen:                       # 안전장치② 중복 호출 차단
                return AgentResponse(answer="...무한루프 방지 장치가 작동...",
                                     steps=steps, stopped_by="duplicate_tool_call")
            seen.add(sig)
            observation = TOOL_MAP[tc["name"]](db, **args)   # 파이썬이 실제 실행
            messages.append(_tool_message(tc["id"], observation))  # 관찰을 되돌림
            steps.append(AgentStep(step=step_no, action=tc["name"],
                                   action_input=args, observation=observation))

세 가지 안전장치가 전부 이 루프 안에 있다. ① max_steps로 무한 반복을 막고, ② 서명 set으로 같은 도구+인자의 재호출을 차단하며, ③ _trim으로 첫 질문(head)과 최근 N개(tail)만 남겨 토큰을 관리한다. 특히 _trim은 tail이 tool 메시지로 시작하면 앞의 assistant를 하나 더 포함해 tool_call ↔ tool 짝을 깨지 않도록 보정한다 — OpenAI 메시지 순서 규칙을 지키는 실무 디테일이다.

의문도구가 실패하면(없는 상품 코드 등) 루프가 멈춰야 하나? 예외를 던지면 에이전트가 죽고, 조용히 넘기면 거짓 답을 만든다. 그 사이 어디에 선을 긋나?

답은 실패를 두 종류로 나누는 것이었다. 비즈니스 실패(없는 상품·주문, 잘못된 인자)는 도구가 {"ok": false, "error_code", "message"} 형태의 구조화된 관찰로 돌려주고, 에이전트는 이걸 보고 사과하거나 재시도한다(멈추지 않음). 반대로 인프라 실패(LLM 서버 다운, DB 오류)는 삼키지 않고 예외로 전파한다. 루프 안에서도 인자 JSON 파싱 실패나 TypeError(인자 개수 불일치)는 bad_arguments 관찰로 흡수하지만, 그 외 예외는 그대로 올린다.

배운 점"도구 오류를 조용히 삼키지 말 것"(공략집 함정 5번)이 왜 중요한지 코드로 잡혔다. 실패를 정상 결과처럼 위장하면 에이전트는 그걸 사실로 믿고 거짓말을 확신한다. 반대로 모든 실패를 예외로 던지면 사소한 오타에도 대화가 죽는다. "예상된 비즈니스 실패는 관찰로, 예상 밖 인프라 실패는 예외로"라는 이분법이, 에이전트를 강건하면서도 정직하게 만드는 경계였다.

CH 05도구 설계 — 좋은 도구 5원칙과 구조화된 실패#

에이전트의 손발인 도구는 app/tools/commerce_tools.py에 6종 있다 — get_price·get_stock·get_order_status·search_product·get_exchange_rate·search_knowledge_base. 스테이지 10의 좋은 도구 5원칙(① 한 가지 일 ② 이름=기능 ③ 명확한 인자 ④ 구체적 독스트링 ⑤ 일관된 반환)을 그대로 지켰다. 모델은 함수 본문이 아니라 이름·인자·독스트링으로 도구를 고르므로, 독스트링이 곧 모델용 프롬프트다.

def get_stock(db: Session, product_code: str) -> dict[str, Any]:
    """상품 코드로 재고와 재주문 필요 여부를 조회한다. 인자: product_code."""
    product = db.query(Product).filter(Product.product_code == product_code).first()
    if product is None:
        return _fail("product_not_found", f"상품을 찾을 수 없습니다: {product_code}")
    inv = db.query(Inventory).filter(Inventory.product_id == product.id).first()
    stock = inv.stock if inv else 0
    reorder = inv.reorder_level if inv else 0
    return {"ok": True, "product_name": product.name, "stock": stock,
            "reorder_level": reorder, "need_reorder": stock <= reorder}

def _fail(code: str, message: str) -> dict[str, Any]:
    return {"ok": False, "error_code": code, "message": message}   # 구조화된 실패

모든 도구가 dict를 반환하고, 실패는 예외 없이 _fail로 통일된다(일관된 반환). 여섯 번째 도구 search_knowledge_base는 특별한데 — 겉으로는 다른 도구와 똑같은 시그니처지만, 내부적으로 app.rag.service.search()를 불러 RAG를 하나의 도구로 감싼다. 에이전트 입장에선 "정책 검색"도 "재고 조회"와 똑같은 도구 하나일 뿐이다. 스테이지 12의 RAG가 스테이지 10의 Function Calling 인터페이스로 흡수된 지점이 바로 여기다.

그 RAG 도구가 부르는 rag/service.py는 스테이지 12의 두 함정을 코드로 방어한다. 인덱스는 서버 기동 시 1회만 load_local해 모듈 캐시에 두고(요청마다 from_documents는 안티패턴), 반환 필드는 score가 아니라 distance다 — FAISS 점수는 거리(작을수록 유사)라 코사인과 반대이기 때문이다.

정리도구 계층의 우아함은 이질적인 것을 같은 모양으로 감싼다는 데 있었다. DB 쿼리(가격·재고·주문), 순수 상수표(환율), 벡터 검색(RAG) — 구현은 완전히 다르지만, 에이전트에겐 모두 "dict를 돌려주는 도구 하나"다. 이 균일한 인터페이스 덕에 스테이지 10~12의 서로 다른 학습이 한 루프 안에서 자연스럽게 조합된다. 통합이 가능했던 진짜 이유는 이 공통 계약(contract)이었다.

CH 06수동 루프 vs LangChain — 원리를 배운 뒤 자동화#

흥미로운 설계 결정 하나 — 통합 앱은 같은 에이전트를 두 경로로 제공한다. 라우터 app/routers/agent.py에 엔드포인트가 둘이다.

@router.post("/chat", response_model=AgentResponse)
def agent_chat(body, db=Depends(get_db)) -> AgentResponse:
    """수동 ReAct 루프 (학습 baseline)."""
    return run_react_agent(body.question, db, max_steps=body.max_steps)

@router.post("/lc-chat", response_model=AgentResponse)
def agent_lc_chat(body, db=Depends(get_db)) -> AgentResponse:
    """LangChain 자동 ReAct (Phase 3.5). 운영 경로 후보."""
    return run_langchain_agent(body.question, db, recursion_limit=body.max_steps * 2 + 2)

/chat은 CH04의 손수 만든 루프이고, /lc-chat은 LangChain create_agent(llm, tools, system_prompt)로 한 줄에 같은 ReAct를 돌린다. 도구는 app/agent/lc_tools.py에서 commerce_tools의 순수 함수를 @tool로 얇게 감싸 재사용한다 — DB 세션을 클로저로 바인딩하고(전역 세션 금지) 반환만 JSON 문자열로 통일한다. 즉 도구 6종은 하나의 진실이고, 두 에이전트가 이를 공유한다.

두 경로가 같은 AgentResponse 스키마(answer·steps·stopped_by)로 응답하는 것이 핵심이다. LangChain 쪽은 결과 메시지에서 ToolMessage를 훑어 AgentStep으로 역추출해, 수동 루프와 응답 모양을 맞춘다. 덕분에 챗 UI는 어느 경로든 동일하게 "에이전트 단계"를 표시할 수 있다.

배운 점왜 손으로 짠 루프를 남겨뒀나 — "원리를 손으로 배운 뒤 프레임워크로 자동화한다"는 커리큘럼의 순서를 아키텍처가 그대로 증명하기 때문이다. 수동 루프는 안전장치 3종·오류 경계를 내가 통제하는 baseline이고, LangChain은 그 원리를 검증한 뒤 얹은 운영 후보다. 운영 경로 단일화는 실키 대조 후로 미뤄 둔, 정직하게 열린 결정이었다. "프레임워크가 뭘 대신 해주는지"는, 직접 짜 본 사람만 안다.

CH 07정직한 완료 상태 — 검증된 것과 이월된 것#

최종 통합 리포트는 "100% 완료"라고 쓰지 않았다. "핵심 구현 완료 + 일부 라이브 항목 실키 이월"이라는 표현이, 이 프로젝트에서 가장 배운 태도였다.

영역검증 상태
전체 테스트CI 108개 + 로컬(실모델 포함) 124개 통과
도구·수동 ReActmock 결정론 테스트 통과 / 라이브 tool-calling은 실키·로컬 Qwen
RAG인덱싱/서비스 분리·FAISS 거리 오름차순·라이브 검색 검증
ML(감성·의도·추천)실모델 pytest 통과(에이전트 도구화는 선택 이월)
tool-calling 메커니즘로컬 Qwen(chatml-function-calling)으로 토큰 0 검증

로컬 Gemma는 OpenAI tool-calling을 미지원이라 요약·분류 같은 평문 작업에만 쓰고, 실제 도구 호출까지 토큰 없이 확인하려면 로컬 Qwen을 썼다(debug_notes에 검증 기록). 완전한 멀티스텝 E2E는 CPU 속도·RAM 여건에 좌우돼, 짧은 라이브 스모크는 사용자 키로 실행하도록 scripts/realkey_smoke.py를 준비해 두고 이월했다 — 안전상 에이전트가 사용자 키를 직접 넣지 않는다는 원칙과 함께.

배운 점오늘 얻은 그림은 이렇다 — 형태소·임베딩(재료) → 딥러닝·BERT(ML 도구) → LLM API·파라미터(인프라·실험실) → 프롬프트·CoT(에이전트 두뇌) → Function Calling·Tool(손발) → Agent Loop·Planning(루프) → RAG·LangChain(기억·자동화)가, 도구라는 공통 계약과 ReAct라는 하나의 루프로 수렴했다. 12개 스테이지가 흩어진 지식이 아니라 하나의 아키텍처를 향한 층위였음을, 합쳐 돌려보고서야 알았다. 그리고 "다 됐다"가 아니라 "여기까지 검증됐고 이건 이월"이라고 쓰는 것 — 그게 학습 프로젝트를 제품 앞에 세우는 마지막 한 걸음이었다.
