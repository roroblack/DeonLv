CH 01왜 통합했나 — 폴더로 흩어진 28개#

문제 인식

6/24 형태소 분석부터 7/10 ReAct 에이전트까지, 커리큘럼은 하루에 한두 개씩 독립 프로젝트를 남겼다. 전처리·임베딩(6/24~25), 딥러닝 분류·생성(6/26~7/02), LLM 활용(7/03~7/08), 에이전트(7/09~7/10). 학습 단위로는 깔끔했지만, 통합 관점에서는 문제가 분명했다.

의문 → 진단 — 왜 재현·연결이 안 되나

의문 28개가 다 돌아가는데, 왜 "하나의 서비스"로 보이지 않나? — 프로젝트마다 설정(common.py 9종)·데이터셋(CSV 4벌 중복)·모델명이 제각각이고, 키가 없을 때 "데모 모드"로 빠지는 폴백이 곳곳에 박혀 있어, 무엇이 실제로 동작하는 코드고 무엇이 가짜 응답인지 구분되지 않았다.
일자별 프로젝트 → 통합 위치 (28개 색인 발췌)
6/30 Bert_sentiment   KoELECTRA 파인튜닝(실모델)  → app/ml/sentiment.py
7/07 fastapi_board     DB·JWT·주문/결제           → app/db·auth·services
7/08 vector_db         FAISS·인덱싱/서비스 분리    → app/rag/
7/09 prompt_console    few-shot·인젝션·분류        → app/prompts/
7/09 planning_console  Plan·검증·재계획            → app/agent/planning.py

배운 점 통합의 베이스는 커리큘럼의 종착점인 react_tools_agent로 두되, 앞 단계의 학습은 각 모듈로 흡수하기로 했다. 단, "흡수"는 코드를 그대로 옮기는 게 아니었다 — 기능은 계승하되 방식은 재현성을 위해 대체되는 경우가 있었다(의도분류는 레거시 PyTorch MLP 대신 규칙기반, 유즈케이스는 5종으로 축소). 학습 방식까지 그대로 이관한 건 감성분석(KoELECTRA 실모델)뿐이었다.
다음으로 — 무엇을 버리고 무엇을 세울지 판단하려면, 먼저 판단 기준이 필요했다. 그게 RULE이다.

CH 02설계 원칙(RULE) — 하드코딩·폴백·데모모드 없음#

세 가지 금지

모든 작업(사람·AI 공통)에 우선하는 RULE.md를 먼저 세웠다. 핵심은 세 가지 금지다. 하드코딩 없음(모델명·경로·가격·SECRET 전부 config), 폴백 없음(오류를 삼켜 그럴듯한 가짜로 대체 금지), 데모모드 없음(키 없을 때 안내문자열을 정상 응답처럼 반환 금지).

의문 → 정의 — "폴백 금지"와 실무 오류 처리는 어떻게 공존하나

의문 키가 없으면 무조건 예외를 던지라는 건데, 그럼 사용자에게 오류를 안내하는 HTTP 응답조차 금지인가? — 아니다. 폴백 금지는 "오류를 삼켜 가짜 결과로 대체하는 것"을 막는 것이지, 오류를 명확히 알리는 것을 막는 게 아니다. 이 경계를 에러 taxonomy로 코드화했다.
상황잘못된 폴백 (금지)올바른 처리 (채택)
API 키 없음데모 응답을 정상처럼 반환ConfigError → 503
DB/인프라 실패빈 리스트 반환InfraError → 503
LLM이 잘못된 JSON임의 기본 dict로 대체재시도(제한) 후 LLMOutputError → 502
도구 실행 예외정상 결과처럼 위장구조화 실패 관찰 {ok:false}
사용자 입력 오류—ValidationErr → 422

이 taxonomy는 app/core/errors.py에 AppError 베이스와 FastAPI 예외 핸들러로 구현되어, 전 라우터가 {ok, error_code, message}로 실패를 노출한다.

class ConfigError(AppError):   http_status = 503; error_code = "config_error"
class InfraError(AppError):    http_status = 503; error_code = "infra_error"
class LLMOutputError(AppError):http_status = 502; error_code = "llm_output_error"
class ValidationErr(AppError): http_status = 422; error_code = "validation_error"
# 재시도는 폴백이 아니다: 정해진 횟수만 재시도하되, 최종 실패는 숨기지 않고 오류로 노출한다.
배운 점 "폴백 금지"를 교조로 두면 실무 오류 처리가 막힌다. 대신 비즈니스 실패(없는 상품)와 인프라 실패(DB 다운·키 부재)를 구분하고, 전자는 에이전트가 관찰할 구조화 실패로, 후자는 명시적 예외로 처리했다. getenv(default="change-this") 같은 레거시 SECRET_KEY 패턴은 이관 시점에 require_secret_key() 가드로 전면 제거했다.
다음으로 — 원칙을 세웠으니, 가장 아래층(실행 골격과 커머스 코어)부터 이 원칙으로 다시 지었다.

CH 04도구 + 수동 ReAct (Phase 3)#

먼저 손으로 — 자동화 이전의 원리

강의 순서를 따라, 프레임워크 자동화(LangChain) 이전에 수동 ReAct 루프를 손으로 구현했다. Thought → Action(도구) → Observation의 반복을 chat_fn 주입형으로 짜서, 모델 없이도 결정론적으로 테스트할 수 있게 했다. 도구는 6종이다.

도구하는 일반환
get_price상품 코드로 가격 조회price / product_not_found
get_stock재고·재주문 필요 여부stock, need_reorder
get_order_status주문번호로 상태·금액status / order_not_found
search_product상품명 키워드 검색results(부분 일치)
get_exchange_rate통화 환율(고정표)rate / currency_not_supported
search_knowledge_base정책·매뉴얼 RAG 검색results (Phase 5 연결)

도구는 "좋은 도구 5원칙"(한 가지 일 / 이름=기능 / 명확한 인자 / 구체적 독스트링=모델 프롬프트 / 일관된 반환)을 따랐다. 예상된 비즈니스 실패는 {"ok": false, ...}로 구조화하되, 인프라 예외는 삼키지 않고 전파한다.

의문 → 안전장치 — 에이전트가 무한 루프에 빠지면

의문 모델이 같은 도구를 계속 부르거나 끝나지 않으면 어떻게 멈추나? — 세 가지 안전장치를 뒀다. max_steps(기본 3, 로컬 CPU 추론이 느려 작게), 중복 호출 서명 차단(name+정렬된 args 해시), History Trimming(head 2개 + 최근 8개, tool 메시지로 시작하면 짝 보정).
sig = _signature(name, args)          # name + json.dumps(args, sort_keys=True)
if sig in seen:
    return AgentResponse(
        answer="동일한 도구와 인자가 반복 호출되어 무한루프 방지 장치가 작동했습니다.",
        steps=steps, stopped_by="duplicate_tool_call")
seen.add(sig)
...
try:
    observation = fn(db, **args)
except TypeError as exc:              # 인자 개수/이름 불일치 → 구조화 관찰
    observation = {"ok": False, "error_code": "bad_arguments",
                   "message": f"도구 인자 오류: {exc}"}
    # 그 외 예외(InfraError 등)는 삼키지 않고 전파 (Codex 합의)
배운 점 Codex 점검에서 실제 크래시 하나가 잡혔다 — 유효한 JSON이지만 인자 개수가 틀리면 fn(db, **args)가 TypeError로 루프 전체를 무너뜨렸다. 이걸 "정상 결과처럼 위장하는 폴백"으로 삼키면 RULE 위반이고, "그냥 전파"하면 에이전트가 학습할 기회를 잃는다. 답은 TypeError만 잡아 bad_arguments 구조화 관찰로 반환하고 나머지 예외는 전파하는 것이었다. ReAct 루프는 mock 결정론 5종(정상·max_steps·중복차단·unknown_tool·bad JSON)으로 검증했고, 테스트는 43 → 49개가 됐다.
다음으로 — 루프 로직은 mock으로 검증됐다. 그렇다면 실제 모델로 라이브 tool-calling을 확인해야 했다. 여기서 이 프로젝트에서 가장 긴 디버깅이 시작됐다.

CH 05로컬 모델 tool-calling 디버깅 (핵심 서사)#

가설 — 로컬 Gemma로 라이브 검증

외부 토큰을 쓰지 않으려고, 빌드 내내 로컬 Gemma를 OpenAI 호환 서버로 띄워 썼다. 서버 구동 자체가 먼저 트러블슈팅이었다 — llama_cpp.server가 sse_starlette·starlette_context를 요구하며 fastapi 0.116.1(starlette<0.48)과 충돌해서, 결국 llama_cpp.Llama를 직접 감싼 최소 OpenAI 호환 서버를 자체 작성했다. 모델 로드도 처음엔 실패했는데, 원인은 아키텍처 미지원이 아니라 컴퓨트 버퍼 할당 실패(여유 RAM 5GB, q4_0 모델 5.1GB)였다. n_ctx=1024, n_batch=32, use_mmap으로 튜닝해 14초 로드에 성공했다.

의문 → 실패 — 도구를 넘겼는데 steps가 비어 있다

의문 구동은 됐고 일반 completion도 잘 나오는데, tools=TOOLS_SCHEMA로 요청하니 steps가 계속 비어 있었다. 도구를 안 부르는 건가, 못 부르는 건가?
로컬 Gemma 라이브 스모크 — "P0001 상품 가격 알려줘" max_steps=2
stopped_by: final_answer
steps: []
answer: '<|tool_call>call:get_price{product_code:"P0001"}...'

원인이 로그에 그대로 있었다. Gemma는 네이티브 tool_calls를 반환하지 않고, content에 유사 tool-call 텍스트를 평문으로 뱉었다. llama-cpp의 OpenAI 어댑터가 이 텍스트를 구조화 tool_calls로 파싱하지 못하니, ReAct 루프는 이걸 최종 답변(text)으로 처리해 버렸다.

의문 → 판단 — 정규식으로 파싱해서 폴백을 붙일까

판단 유혹은 있었다 — <|tool_call>call:...을 정규식으로 파싱해 도구 실행으로 연결하면 로컬에서도 돌아간다. 그러나 이 포맷은 Gemma 특유이고 극히 취약하다. RULE 3.3(YAGNI·취약 코드 금지)에 따라 정규식 폴백은 추가하지 않기로 했다. 루프 로직은 mock 결정론 5종으로 이미 검증됐으니, 라이브 tool-calling은 실키(OpenAI/Gemini)로 이월했다.

의문 → 해결 — 키 없이 로컬에서 tool-calling을 증명할 수 있나

이월했던 항목을 캐시된 Qwen 모델로 다시 시도했다. chat_format="chatml-function-calling"으로 로드하고 get_price 도구를 넘긴 결과다.

로컬 Qwen(chatml-function-calling) — tool-calling 검증 · 토큰 0
tool_calls: [{'id': 'call__0_get_price_...', 'type': 'function',
  'function': {'name': 'get_price', 'arguments': '{ "product_code": "P0001" }'}}]
HAS_TOOLCALL: True
배운 점 Qwen은 정확한 OpenAI 형식 tool_calls를 반환했다 — 즉 tool-calling 미지원은 로컬 모델 전체의 한계가 아니라 Gemma라는 특정 모델의 채팅 포맷 문제였다. 모델별로 정리하면: Gemma=평문 전용(tool-calling X), Qwen=tool-calling O(로컬 토큰 0), OpenAI/Gemini=실키. 다만 Qwen 4B는 CPU 추론이 요청당 수 분이고 RAM 2.5GB가 상주해, 단일 도구호출 메커니즘은 검증했으나 풀 멀티스텝 E2E는 자원 여건에 좌우된다. 정규식 폴백을 안 붙인 판단이 옳았다는 걸, 더 나은 모델로 증명한 셈이다.
다음으로 — 수동 루프로 원리를 이해했으니, 이제 강의 후반의 핵심인 "프레임워크로 자동화"로 넘어간다.

CH 06LangChain 자동화 계층 (Phase 3.5)#

원리를 배웠으니, 자동화

강의 후반의 메시지는 분명했다 — "수동 루프로 원리를 손으로 구현한 뒤, LangChain으로 자동화한다." 이 후반부가 초기 계획서엔 빠져 있어서 신규 Phase 3.5로 끼워 넣었다. 커머스 도구를 @tool로 재정의하되 Phase 3 도구를 재사용(중복 구현 금지, db 클로저 바인딩)하고, create_agent(llm, tools, system_prompt)로 자동 ReAct를 구성했다. 운영 경로는 /api/agent/chat(수동)과 /api/agent/lc-chat(LangChain)의 이중 경로로 뒀다.

의문 → 결정 — 두 경로를 둘 다 영구 유지할 것인가

의문 수동 ReAct와 LangChain을 둘 다 제품 경로로 유지하면 같은 기능이 두 벌이 된다(YAGNI 위반). 어느 쪽을 남길까? — Codex 2차 리뷰의 방침을 따랐다. 수동 루프는 학습·비교용 baseline으로 1회 대조 리포트를 남긴 뒤 동결하고, 운영은 LangChain 하나로 수렴한다.
run_langchain_agent 라이브 플러밍 (로컬 Gemma)
run_langchain_agent('간단히 인사해줘') →
stopped_by: final_answer, steps: 0, answer_len: 38, LC_PLUMBING_OK
배운 점 get_langchain_chat은 local/openai=ChatOpenAI, gemini=ChatGoogleGenerativeAI로 분기하되 모두 키·모델명 미설정 시 ConfigError를 던진다(폴백 없음). 라이브 플러밍에서 create_agent→invoke→step추출→AgentResponse 전 경로가 크래시 없이 돌았고, steps=0은 CH05에서 확인한 Gemma 제약과 정확히 일치했다. 다만 실제 단일화는 실키 대조 후로 이월했다 — 로컬 Gemma로는 수동 vs LangChain의 도구 호출을 나란히 비교할 수 없기 때문이다. 정직하게 "병존 유지"로 남겼다. 테스트는 56 → 61개.
다음으로 — 에이전트가 도구를 부르기 전에, 먼저 사용자의 의도를 정확히 읽어야 한다. 프롬프트·분류·Planning 계층이다.

CH 07프롬프트·분류·Planning (Phase 4)#

결정론적 분류 + 인젝션 방어

CS 문의 60건을 7카테고리로 분류하는 파이프라인을 이관했다. temperature=0 결정론 분류에, 사용자 입력을 구분자로 감싸는 인젝션 방어(wrap_user_input + HARDENED_ROLE), few-shot 프롬프트를 붙였다. 모델 출력에서 카테고리가 정확히 1개면 반환, 0개나 2개 이상이면 '미분류' sentinel로 처리한다(측정에서만 오답).

라이브 분류 — CS 문의 8건 (로컬 Gemma 평문 completion)
preds  : 결제 환불 상품문의 교환 배송 칭찬 교환 배송
labels : 결제 환불 상품문의 교환 배송 칭찬 교환 배송
accuracy(8건 참고치): 1.0 (8/8)

Gemma는 tool-calling은 못 해도 평문 few-shot 분류는 정확히 수행했다(CH05에서 확인한 "일반 completion은 유효" 범위). 프롬프트+분류+측정 파이프라인이 라이브로 검증됐다.

의문 → 루프 — 오분류를 어떻게 체계적으로 줄이나

의문 정확도 한 숫자로는 "무엇이 무엇으로 잘못 분류되는지"를 모른다. 어떻게 약한 경계를 찾아 보강하나? — 측정 → 혼동쌍 집계(Counter) → few-shot 후보 산출 → 전후 비교의 순환으로 닫았다. 자동 재작성은 YAGNI로 두지 않았다(후보 산출까지만).
def confusion_pairs(preds, labels):        # 오분류된 (정답, 예측) 쌍 집계
    counter = Counter()
    for pred, lab in zip(preds, labels):
        if pred != lab:
            counter[(lab, pred)] += 1
    return dict(counter)

def improvement_report(...):               # 루프를 하나의 리포트로 닫는다
    before = measure_accuracy(_run(base_fewshot), labels)     # 측정
    pairs  = confusion_pairs(...)                             # 분석
    after  = measure_accuracy(_run(augmented_fewshot), labels)# 처방 후 재측정
    return {"before_accuracy": ..., "after_accuracy": ..., "delta": ...}

Planning은 Plan-and-Execute다. Pydantic Plan(goal + steps)을 with_structured_output으로 생성하고, validate_plan이 단계 수(MIN 2 / MAX 8)·빈 단계를 검사한 뒤 실패 시 재계획한다.

배운 점 Codex 점검에서 plan_with_validation이 구조화 출력 예외를 그대로 전파하던 결함이 잡혔다. 이걸 _attempt로 감싸 예외를 '문제'로 흡수해 재계획 대상으로 삼되, max_replan 초과 후에도 실패하면 LLMOutputError로 노출하게 고쳤다. "조용히 삼키는 폴백"과 "재시도 후 명확한 실패"의 경계를 여기서도 지켰다. make_plan 라이브는 Gemma tool-calling 제약으로 실키 이월. 테스트는 78 → 81개.
다음으로 — 정책·매뉴얼처럼 DB에 없는 지식은 문서 검색으로 답해야 한다. RAG 계층이다.

CH 08RAG — 인덱싱과 서비스의 분리 (Phase 5)#

인덱싱은 1회, 서비스는 매 요청

강의가 가장 강조한 지점은 인덱싱과 서비스의 분리였다. "요청마다 from_documents"라는 안티패턴을 피해, build_index.py(사전 1회: txt→청킹→FAISS→save_local)와 service.py(서버 기동 시 load_local 1회 로드, 모듈레벨 캐시)를 나눴다. 임베딩은 로컬 ko-sroberta-multitask(토큰 0), 청킹은 CHUNK 400 / OVERLAP 50 / TOP_K 3이다.

의문 → 함정 — 점수가 큰 게 더 유사한 건가

의문 similarity_search_with_score의 점수를 유사도로 착각하면 정렬이 뒤집힌다. FAISS의 이 점수는 거리(작을수록 유사, 코사인과 반대)다. 반환 필드명을 distance로 명시하고 오름차순 정렬, 무관한 결과는 RAG_MAX_DISTANCE=1.5 초과로 걸러냈다.
라이브 검색 — search_knowledge_base('ReAct 에이전트 무한루프 방지')
ok=True, count=3, top source=loop_safety.txt, distance=92.174   ← 관련 문서 1순위

로컬 Gemma 요약(map-reduce):
  "ReAct 에이전트는 '생각','행동','관찰'의 과정을 반복하며 작동합니다.
   안전을 위해 최대 단계 수를 제한하고, 동일한 도구 호출의 반복을 막습니다..."
  SUMMARIZE_OK
배운 점 Codex 점검에서 RAG 테스트가 실 data/vector_store를 오염시키던 문제(→ tmp_path 격리)와, 무관한 질의도 top-k를 반환하던 문제(→ 임베딩 정규화 + 거리 임계값 필터, 무관 질의는 [])를 고쳤다. add_documents도 원문 그대로가 아니라 build_index와 동일한 splitter로 청킹 후 증분 추가하도록 통일했다. allow_dangerous_deserialization은 자체 생성 인덱스만 로드한다는 전제를 주석으로 못박았다. 테스트는 88 → 91개.
다음으로 — 도구·RAG 다음은 ML 분류·추천이었고, 마지막엔 강의 전체를 다시 읽으며 스스로 빠진 것을 찾았다.

CH 09ML·추천 + 커버리지 자가감사 (Phase 6~7)#

실모델 재사용 — KoELECTRA 감성

Phase 6은 ML 서비스다. 의도분류는 규칙기반(7의도, 동률 (매칭수, -우선순위) tie-break), 감성분석은 6/30 Bert_sentiment에서 학습한 KoELECTRA NSMC 실모델을 재사용(lazy 캐시, 라벨은 하드코딩 대신 id2label에서 해석), 추천은 ko-sroberta 임베딩 코사인 top_k다. 감성은 로컬 실모델이라 토큰 0으로 검증됐다.

Phase 6 검증 — 실모델 포함 (ml 마커)
$ pytest -m "not llm and not ml"   (CI 경로)   88 passed, 17 deselected
$ pytest -m "ml"   (rag+sentiment+recommend)   15 passed

감성(실 KoELECTRA): "정말 좋아요 만족" → 긍정 / "최악 고장 환불안돼" → 부정 ✓
추천(임베딩 코사인): "무선 이어폰" → top_k 3개 점수 내림차순 ✓

의문 → 자가감사 — 강의 개념 중 무엇을 빠뜨렸나

의문 구현을 다 했다고 믿기 전에, 정말 강의 개념을 다 담았을까? — 강의 PDF 6종(0703~0710, 40~84p)을 PyMuPDF로 추출해 전량 정독하고, 계획서와 대조했다. 가장 중요한 누락 5가지가 나왔다.
누락 항목조치

Phase 7은 실험실·UI였다. lab에 파라미터 실험(basic/role/diversity), 한↔영 토큰 비교(한국어 토큰 > 영어), 비용 추정(PRICE_TABLE config화, 로컬은 과금 없음→ConfigError), 기능별 유즈케이스 5종(요약/번역/이메일/코드/문제)을 담았다.

배운 점 구현 자신감이 아니라 강의 원문과의 대조가 누락을 드러냈다. 특히 "수동 루프로 원리 → LangChain으로 자동화"의 후반부가 통째로 빠져 있었던 게 가장 컸고, 이걸 Phase 3.5로 메운 것이 이 프로젝트의 방향을 바꿨다. tiktoken 토큰 수는 cl100k 참고치로 명시했다(Gemma 실토큰 아님). 자가감사 없이 "완료"를 선언했다면 강의 핵심의 절반을 놓쳤을 것이다.
다음으로 — 7개 Phase를 다 돌았다. 마지막은 이 결과를 어떻게 정직하게 보고하느냐였다.

CH 10정직한 마무리 — 통과와 이월#

"100% 완료"라고 쓰지 않는다

전 Phase를 마친 뒤, 최종 보고를 "100% 완료"로 쓰지 않았다. RULE 1(과장 금지)에 따라 "핵심 구현 완료 + 일부 라이브 항목 실키 이월"로 적었다. 이 정직함 자체가 RULE의 첫 조항이다 — 검증 없이 "완료"를 선언하지 않는 것.

최종 상태 — 테스트 통과 / 실키 이월
테스트: CI 108 + 로컬(실모델 포함) 124 통과, 실키 필요 2개 이월
구동 스모크: 12/12 통과 (health·상품·주문·결제·의도·감성·추천·토큰·비용·503·RAG·UI)
tool-calling: 로컬 Qwen으로 메커니즘 검증(토큰0), 풀 E2E는 자원·키 여건

이월 2건 (scripts/realkey_smoke.py):
  1. 에이전트 라이브 tool-calling (steps 채워짐) — 사용자 키 필요
  2. 실키 대조 후 운영 경로 LangChain 단일화 결정
  ⚠️ 안전상 에이전트는 사용자 키를 입력하지 않음. 키 설정은 사용자가 수행.

잔여 리스크 — 숨기지 않는다

잔여 리스크 (1) 운영 에이전트 경로가 수동/LangChain 병존 → 실키 대조 후 단일화. (2) ML은 /api/nlp/* 독립 API로, 에이전트에 도구로 연결하지 않음(아키텍처 결정). (3) 로컬 Gemma는 RAM 5.5GB+ 필요·CPU 추론 느림. (4) tiktoken은 참고치(Gemma 실토큰 아님).
관통 교훈 네 가지
  1. 흡수 ≠ 복사. 28개를 통합하며 기능은 계승하되 방식은 재현성을 위해 대체됐다 — 이관은 코드 이동이 아니라 재설계였다.
  2. 폴백 금지의 경계. 오류를 삼키는 폴백은 금지하되, 명시적 예외와 구조화 실패 관찰은 정상 처리다. 이 경계를 taxonomy로 코드화한 것이 통합 전체를 지탱했다.
  3. 취약한 우회를 붙이지 않는 판단. Gemma 평문을 정규식으로 파싱하는 폴백을 참고, mock으로 루프를 검증하고 Qwen으로 메커니즘을 증명했다 — YAGNI가 옳았다.
  4. 정직한 보고가 마지막 원칙. "완료 = 100%"가 아니라 "핵심 구현 + 실키 이월"로 적고 잔여 리스크를 나열하는 것 자체가 RULE 1이다.

주차 회고는 11주차 회고로 이어진다. 하루 단위 기록은 7/03 LLM 개념부터 7/09 ReAct 커머스 에이전트까지에 남겨 두었다.
