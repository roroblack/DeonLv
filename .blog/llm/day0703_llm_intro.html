LLM 개념과 API — 초거대언어모델의 이해와 사용

지난 단원까지 임베딩·트랜스포머로 "문맥을 벡터로 읽는 법"을 쌓아왔다. 오늘은 그 흐름이 어디로 이어졌는지 — 트랜스포머를 대규모로 사전학습해 하나의 모델로 여러 작업을 처리하는 LLM, 그리고 그것을 코드가 아닌 API 호출로 쓰는 방식(토큰·컨텍스트·파라미터)을 개념 중심으로 정리한다. API 키가 없어 실제 호출 대신 개념과 사용법에 집중한다.

여기까지 딥러닝 단원에서 RNN·LSTM의 정보 병목을 봤고, 어텐션과 트랜스포머로 "순서를 버리고 문장 전체 관계를 한 번에 읽는" 구조까지 왔다. 그런데 강의 노트를 되짚다 계속 걸린 지점이 있었다. 트랜스포머는 구조일 뿐인데, 어떻게 그게 번역·요약·코드작성을 한꺼번에 하는 하나의 제품이 된 걸까. 오늘 강의는 그 빈칸 — 구조에서 LLM으로 — 을 메우는 시간이었다.

CH 01LLM이란 무엇인가#

LLM은 Large Language Model, 대규모 언어 모델이다. 강의는 그 상징으로 2020년 공개된 GPT-3를 든다. 1,750억 개 파라미터를 가진 자기회귀(auto-regressive) 언어 모델로, 여기서 자기회귀란 앞의 토큰들을 보고 다음 토큰을 예측하는 방식을 뜻한다. 지난 언어 모델 글에서 LSTM이 다음 단어를 확률로 맞추던 그 원리가, 트랜스포머 위에서 압도적 규모로 반복된 것이다.

의문노트를 정리하며 막혔던 질문. 트랜스포머는 Attention Is All You Need에서 본 '아키텍처'인데, 그 구조 자체가 어떻게 질문답변·번역·요약을 다 하는 하나의 모델이 되나? 구조와 능력 사이에 뭐가 채워진 건가.

강의가 채워준 빈칸은 사전학습(Pre-training)과 스케일(scale)이었다. 사전학습은 LLM을 만들 때 가장 먼저 하는 대규모 학습 단계로, 인터넷 문서·책·코드·위키 같은 방대한 텍스트에서 오직 "다음 토큰 맞추기"만 반복한다. 입력이 "인공지능은 데이터를 학습하여"라면 정답은 "패턴" 같은 식이다. 이 단순한 과제를 거대한 데이터로 충분히 반복하면 모델은 문장 구조, 단어 의미 관계, 문맥, 상식적 표현, 코드 패턴, 질문-답변 구조까지 부수적으로 습득한다. 즉 사전학습은 언어의 기본 능력을 통째로 갖추는 과정이다.

배운 점GPT-3가 준 진짜 메시지는 성능 수치가 아니라 "모델 크기를 크게 키우면 별도의 세부 학습 없이도 여러 작업을 수행한다"는 관찰이었다. 기존 NLP는 감성분석·번역·요약·질의응답을 작업마다 따로 학습시켜야 했다. LLM 이후로는 하나의 모델이 프롬프트만 바꿔 여러 작업을 처리한다. 트랜스포머라는 '구조'가 '제품'이 된 지점이 바로 여기 — 스케일이 붙은 사전학습이었다.

CH 02모델의 종류와 재학습 없이 쓰는 법#

LLM은 하나로 뭉뚱그려지지만 구조와 목적에 따라 갈린다. 앞선 논문 글에서 본 GPT 계열(생성)과 BERT 계열(이해)의 분기가 여기서 종류표로 정리됐다.

종류설명예시
Decoder-only이전 토큰을 보고 다음 토큰을 생성GPT 계열
Encoder-only문장을 이해하고 분류하는 데 강함BERT 계열
Encoder-Decoder입력 문장을 다른 문장으로 변환T5, BART
Instruction-tuned사람의 지시를 잘 따르도록 추가 학습InstructGPT, ChatGPT 계열
Multimodal텍스트뿐 아니라 이미지·음성 등도 처리GPT-4o 계열

GPT 계열은 글쓰기·답변·코드작성·요약·번역·챗봇처럼 생성형 작업에, BERT 계열은 문장분류·감성분석·개체명 인식·유사도·검색 랭킹처럼 이해 기반 작업에 강하다. 즉 지난 임베딩 글에서 짚은 "고정 임베딩 → 문맥 임베딩(BERT/GPT)"의 두 갈래가, 그대로 오늘의 두 모델 계열로 이어진다.

그런데 여기서 결정적으로 궁금했던 건 파인튜닝과의 관계였다. 작업마다 모델을 다시 학습시키는 게 아니라면, 실제로는 어떻게 원하는 작업을 시키는가?

정리In-context Learning이 그 답이다. 모델을 다시 학습(파인튜닝)시키지 않고, 프롬프트 안에 설명이나 예시를 넣어 원하는 작업을 시키는 방식이다. 예컨대 "다음 문장의 감성을 긍정/부정으로 분류하라"는 지시에 예시 문장 두어 개를 붙이면, 모델은 그 패턴을 보고 마지막 문장의 답을 생성한다. 장점은 명확하다 — 별도 학습 데이터셋을 만들거나 모델을 재학습할 필요가 없다. 사전학습으로 얻은 범용 능력을 프롬프트로 '지시'만 하는 것이다.

CH 03프롬프트와 예시 개수, 그리고 환각#

프롬프트(Prompt)는 LLM에게 전달하는 입력 지시문이다. 단순 질문일 수도, 역할·조건·출력 형식을 담은 상세 명령일 수도 있다. 강의의 대비가 인상적이었다. 나쁜 프롬프트는 "LLM 설명해줘." 한 줄이고, 좋은 프롬프트는 "너는 인공지능 강사이다. LLM의 개념을 … 정의·학습 방식·Transformer 구조·API 활용·실무 사례를 포함해 설명하라"처럼 역할과 항목을 지정한다. 프롬프트 품질이 답변 품질을 좌우한다.

In-context Learning은 예시를 몇 개 주느냐로 세 갈래가 된다.

방식예시 개수특징
Zero-shot0개예시 없이 바로 지시
One-shot1개예시 하나로 답변 형식을 보여줌
Few-shot여러 개원하는 답변 패턴을 여러 개로 제시 → 결과가 더 안정적

배운 점지난 GPT-3 논문 글(Language Models are Few-Shot Learners)에서 본 제목의 의미가 여기서 맞물렸다. 강의도 같은 점을 짚는다 — 모델을 큰 규모로 확장하면 few-shot 성능이 크게 향상된다는 것. 예시를 주기만 해도 재학습 없이 새 작업을 배우는 이 능력 자체가 스케일의 산물이었다. '구조 → 사전학습 → 스케일 → few-shot'으로 흐름이 하나로 꿰였다.

다만 LLM은 만능이 아니다. 환각(Hallucination)은 사실이 아닌 내용을 그럴듯하게 생성하는 현상으로, 존재하지 않는 논문 제목이나 없는 API 함수, 출처 없는 통계를 자신 있게 지어낸다. 보완책은 RAG 적용, 공식 문서·DB 조회 기반 답변, 출처 표시, 검증 로직과 사람 검토 단계 추가 등이다. 핵심은 "LLM에게 전부 맡기지 말고 외부 데이터와 연결하라"는 것 — 사용자 질문 → 관련 문서 검색 → 검색된 문서를 LLM에 제공 → 근거 기반 답변, 이 구조가 RAG다. (RAG·Function Calling은 뒤 단원의 주제로 예고만.)

CH 04API로 부른다는 것 — 토큰과 컨텍스트#

API 방식은 Python·JavaScript·Streamlit 같은 프로그램에서 LLM 서버를 호출하는 방식이다. 기본 흐름은 사용자 입력 → 앱에서 API 요청 생성 → LLM 서버가 응답 생성 → 앱 화면에 출력. 강의의 Python 예시를 개념용으로 옮기면 다음과 같다. 실제 실행 로그가 아니라 사용 형태를 보여주는 의사(擬似) 코드다 — 이 글에서는 API 키가 없어 호출하지 않았다.

import os
from openai import OpenAI

# API Key를 코드에 직접 쓰면 노출 위험이 있으므로 환경변수에서 읽는다
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

user_input = "LLM에서 zero-shot과 few-shot의 차이를 설명해줘."

# 모델에게 응답 생성을 요청한다 (개념용 — 실제 호출 아님)
response = client.responses.create(
    model="gpt-...",       # 사용할 LLM 모델 지정
    input=user_input,
)

print(response.output_text)  # 모델이 생성한 최종 텍스트

여기서 API를 이해하는 핵심 단위가 토큰(Token)이다. LLM은 문장을 토큰 단위로 읽고 생성하며, 과금도 대체로 토큰 사용량 기준이다. 토큰은 단어와 완전히 같지 않다 — 영어는 짧은 단어 단위로, 한국어는 조사·어절·부분 문자열 단위로 쪼개질 수 있다. 지난 전처리 글에서 BPE(Byte Pair Encoding) 서브워드 토큰화를 봤던 그 결과물이, API에서는 그대로 비용의 단위가 된다.

의문토큰이 곧 비용이라면, "긴 대화를 이어가면" 무엇이 쌓이는 건가? 내가 보낸 질문만 계산되나, 아니면 이전 대화 전체가 매번 다시 들어가나?

토큰 유형무엇인가포함되는 것(예)
Input 토큰API에 보낸 모든 입력System·User 메시지, 예시, 검색된 문서, 이전 대화 기록, 코드·표
Output 토큰모델이 생성한 응답설명·코드·요약·번역·분석·JSON 결과
Cached 토큰이전 입력이 캐시되어 할인 적용될 수 있는 토큰반복되는 입력의 일부

배운 점의문의 답이 여기 있었다. 이전 대화 기록이 Input 토큰에 포함된다 — 즉 대화가 길어질수록 매 요청에 과거 맥락이 함께 실려 입력 토큰이 누적된다. 이것이 컨텍스트 윈도우(모델이 한 번에 다룰 수 있는 토큰 범위)를 관리해야 하는 이유다. 총 사용 토큰 = Input + Output이므로(예: 입력 1,000 + 출력 500 = 1,500), 비용 절감은 관련 없는 긴 문서 제거, 출력 길이 제한, 요약본 사용, RAG로 필요한 문단만 전달, 시스템 프롬프트 최소화로 이어진다. "좋은 프롬프트 · 정확한 외부 데이터 연결 · 토큰과 비용 관리" — 강의가 꼽은 실무 3요소다.

CH 05생성 제어 파라미터 — 창의성·후보·길이#

API 호출에는 답변의 성격을 조절하는 파라미터가 붙는다. 보조 강의자료가 꼽는 세 가지는 Temperature · Top P · Maximum Tokens로, 각각 생성의 창의성·후보 단어 범위·출력 길이를 제어한다. 앞서 본 "다음 토큰을 확률로 고른다"는 원리를 떠올리면 셋 다 그 확률 분포를 어떻게 다룰지에 대한 설정임이 보인다.

  • Temperature — 얼마나 다양한 단어를 고를지. 값이 낮을수록 확률이 가장 높은 단어를 우선 골라 답이 안정적·일관적이고, 높을수록 확률이 낮은 단어도 골라 표현이 다양·창의적이 된다.
  • Top P — 후보 단어의 범위를 누적 확률로 자른다(Nucleus Sampling). 값이 작으면 안정적인 단어만, 크면 다양한 단어까지 후보에 넣는다.
  • Maximum Tokens — 생성할 최대 출력 길이 제한. 작으면 짧고 빠르고 저렴, 크면 긴 설명이 가능하나 비용·응답시간이 는다.

Top P의 감이 잡히지 않았는데, 강의의 예가 명료했다. 다음 단어 확률이 사과 40% · 배 25% · 포도 15% · 딸기 10% … 라면, Top P = 0.5는 누적 50%까지인 {사과, 배}만 후보로 쓰고, Top P = 0.9는 누적 90%까지 넓혀 {사과, 배, 포도, 딸기}를 후보로 삼는다. 즉 "가장 유력한 답만 볼지, 여러 가능성을 함께 볼지"의 조절이다.

작업 유형TemperatureTop PMax Tokens이유
분류0~0.20.8~1.0100~300항상 같은 결과가 중요
정보 추출0~0.20.8~1.0200~500정확성이 중요
일반 설명0.3~0.50.8~1.0500~1000자연스러운 답변
아이디어 생성0.7~1.00.9~1.01000 이상다양성이 중요
소설 작성0.8~1.01.02000 이상창의성이 중요
 
# 파라미터를 함께 지정한 형태 (개념용 — 실제 호출 아님)
response = client.responses.create(
    model="gpt-...",
    input="LLM의 주요 파라미터를 설명해줘.",
    temperature=0.3,          # 안정적·일관성 있는 답변
    top_p=0.9,                # 누적 90% 후보에서 자연스러운 다양성
    max_output_tokens=500,    # 응답 길이·비용 제한
)
print(response.output_text)

배운 점세 파라미터는 결국 하나의 축으로 이어진다. 정확성이 중요하면 Temperature를 낮게, 창의성이 필요하면 높게. Top P를 함께 조절해 다양성을 세밀하게 다루고, Max Tokens로 길이와 비용까지 잡는다. 오늘 잡은 그림은 이렇다 — 트랜스포머(구조)를 대규모로 사전학습해(스케일) LLM(제품)이 되고, 그걸 프롬프트로 지시하며 API 한 줄로 부르되(토큰·컨텍스트), 파라미터로 답변의 성격을 조율한다. 다음은 이 두뇌에 도구·기억을 붙이는 에이전트와 RAG로 이어진다.
