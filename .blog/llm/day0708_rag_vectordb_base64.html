Vector DB · RAG · LangChain — 문서를 임베딩해 넣고, 질문으로 검색해 LLM에 붙이기

9주차에 Word2Vec·FastText로 단어를 벡터로 바꾸고, 지난 LLM 글에서 "환각을 줄이려면 외부 데이터와 연결하라"는 예고를 남겨뒀다. 오늘은 그 빈칸을 메운다 — 정책·매뉴얼 같은 문서를 청킹→임베딩→벡터DB에 넣고, 사용자의 자연어 질문을 같은 벡터공간에서 검색해 LLM 프롬프트에 붙이는 RAG를 실제로 만든다. 통합 커머스 에이전트의 "상품·정책 지식 검색"(search_knowledge_base 도구)이 오늘의 결과물이고, FAISS 인덱싱/서비스 분리와 "점수=거리"라는 함정까지 실측 코드로 짚는다.

지난 LLM 글 마지막에 이렇게 적어뒀다 — "사용자 질문 → 관련 문서 검색 → 검색된 문서를 LLM에 제공 → 근거 기반 답변, 이 구조가 RAG다." 그때는 문장 한 줄로 예고만 했는데, 정작 관련 문서 검색을 어떻게 하는지가 통째로 빈칸이었다. 키워드 매칭이면 "환불"과 "반품"은 못 잇고, 전량 비교면 문서가 늘수록 느려진다. 오늘 채운 빈칸은 바로 그 검색이다 — 9주차에 배운 임베딩(단어→벡터)을 문장 단위로 확장하고, 그 벡터들을 벡터DB에 담아 "질문 벡터와 가까운 문장"을 빠르게 찾는다. 통합 커머스 에이전트가 "반품 정책 알려줘"에 지어내지 않고 실제 정책 문서를 근거로 답하게 만드는 것이 목표였다.

CH 01왜 RAG인가#

RAG(Retrieval-Augmented Generation, 검색증강생성)는 질문과 관련된 문서를 벡터 검색으로 찾아 프롬프트에 넣어주고, LLM이 그 근거로 답하게 하는 방식이다. 지난 글에서 짚은 환각(존재하지 않는 정책·없는 규정을 자신 있게 지어내는 현상)을 실무적으로 줄이는 표준이자, 사내 문서·최신 정보처럼 모델이 학습하지 못한 지식을 답변에 반영하는 통로다. 강의 공략집의 표현을 빌리면 에이전트의 "장기 기억"에 해당한다.

의문지난 글에서 "외부 데이터와 연결하라"까지는 이해했다. 그런데 사용자가 "반품 며칠 걸려요?"라고 물으면, 수십 개 정책 문서 중 어느 문단을 프롬프트에 넣을지를 코드는 어떻게 고르나? 문서에 "반품"이라는 단어가 없고 "교환·환불"만 있으면 놓치는 것 아닌가.

핵심 파이프라인은 이렇다. 문서 → 청킹 → 임베딩 → 인덱스 → 디스크 저장(영속화) → (질문) 질문 임베딩 → 유사도 검색(top_k) → 프롬프트에 문맥 주입 → LLM 답변. 이 중 "어느 문단을 고르나"의 답은 임베딩과 유사도 검색에 있다 — 단어가 겹치는지가 아니라 의미가 가까운지로 찾기 때문에 "반품"과 "환불"도 이어진다. 다음 장에서 그 벡터 공간부터 손에 잡는다.

배운 점RAG는 LLM을 다시 학습시키는 게 아니다. 지난 글의 파인튜닝이 가중치를 바꿔 지식을 넣었다면, RAG는 가중치를 그대로 둔 채 프롬프트에 근거 문서를 실어 지식을 넣는다. 문서가 바뀌면 인덱스만 다시 만들면 되고 모델은 건드리지 않는다 — 정책이 자주 바뀌는 커머스에서 재학습보다 압도적으로 현실적인 이유다.

CH 02임베딩과 벡터DB — 문장을 벡터로#

9주차에 Word2Vec·FastText로 단어를 벡터로 바꿨다. RAG는 이걸 문장·문단 단위로 확장한다 — 문장 임베딩 모델이 한 청크를 고정 길이 벡터 하나로 바꾸면, "의미가 비슷한 문장은 벡터 공간에서 가깝다"는 성질이 그대로 성립한다. 통합 앱에서는 로컬 한국어 문장 임베딩 모델 jhgan/ko-sroberta-multitask를 썼다. 외부 API 토큰을 쓰지 않는 로컬 모델이라 비용이 0이고, 해시 기반 가짜 임베딩으로 대충 때우는 폴백은 두지 않았다(RULE §7 — 실제 임베딩만).

from langchain_huggingface import HuggingFaceEmbeddings

# 정규화하면 L2 거리가 [0,2]로 유계 → 거리 임계값(RAG_MAX_DISTANCE)이 의미를 가짐
return HuggingFaceEmbeddings(
    model_name=model,                                # config의 ST_EMBEDDING_MODEL(하드코딩 금지)
    encode_kwargs={"normalize_embeddings": True},
)

그 다음 필요한 게 벡터DB다. 문서가 수백·수천 청크면 질문 벡터와 전부를 하나씩 비교(NumPy 전량 비교)하는 건 느리다. 벡터DB는 ANN(근사 최근접 이웃)으로 전량 비교 대신 근사 검색을 빠르게 하고, 만든 인덱스를 디스크에 저장해 재사용한다. 실습 프로젝트(vector_db_pycharm_project)에서 01_numpy_limit_demo.py가 전량 비교의 한계를, 02_vector_db_role.py가 벡터DB의 역할을 먼저 짚고 넘어가는 순서였던 이유가 여기 있다.

정리임베딩과 벡터DB의 역할 분담. 임베딩은 "문장 → 벡터"(의미를 좌표로), 벡터DB는 "질문 벡터와 가까운 벡터 top_k 빠르게 찾기"(좌표 위 최근접 탐색)를 맡는다. 9주차 임베딩 글이 앞 절반을, 오늘 벡터DB가 뒤 절반을 채워 "의미 기반 검색"이 완성된다.

CH 03인덱싱과 서비스를 나눈다#

강의(VectorDB.pdf)가 가장 강하게 짚은 설계 결정이 인덱싱과 서비스의 분리였다. 임베딩과 인덱스 생성은 비싼 작업이다. 그런데 요청이 올 때마다 FAISS.from_documents(...)로 전체를 다시 임베딩하면 — 이게 치명적 안티패턴이다. 그래서 코드를 두 축으로 나눴다. 인덱싱(사전 1회)은 문서를 청킹·임베딩해 인덱스를 디스크에 저장하고, 서비스(로드 1회)는 서버 기동 시 저장된 인덱스를 한 번만 로드해 이후엔 검색만 한다.

인덱싱 쪽은 txt 문서를 RecursiveCharacterTextSplitter로 청킹(chunk_size=400, overlap=50)한 뒤 FAISS 인덱스로 만들어 save_local한다. 통합 앱의 실제 build_index.py 핵심은 이렇다.

from langchain_community.vectorstores import FAISS
from langchain_text_splitters import RecursiveCharacterTextSplitter

docs = _load_txt_docs(docs_dir)                              # data/docs/*.txt → Document
splitter = RecursiveCharacterTextSplitter(
    chunk_size=settings.CHUNK_SIZE, chunk_overlap=settings.CHUNK_OVERLAP
)
chunks = splitter.split_documents(docs)

store = FAISS.from_documents(chunks, get_embeddings())       # 여기서만 임베딩(비싼 작업)
store.save_local(str(out_dir))                               # index.faiss + index.pkl
# 어떤 임베딩 모델로 만든 인덱스인지 기록(모델 바뀌면 재빌드 판단용)
(out_dir / ".embedding_model").write_text(settings.ST_EMBEDDING_MODEL)

서비스 쪽은 모듈 레벨 캐시(_store)에 인덱스를 한 번만 로드해 둔다. FAISS를 load_local할 때는 allow_dangerous_deserialization=True가 필요한데, 이건 내가 직접 만든 신뢰할 수 있는 인덱스에만 써야 한다(외부에서 받은 pickle은 절대 로드 금지 — 임의 코드 실행 위험).

_store = None  # 모듈레벨 캐시 (로드 1회)

def get_store():
    global _store
    if _store is not None:                          # 두 번째 요청부터는 재로드 안 함
        return _store
    from langchain_community.vectorstores import FAISS
    # 자체 생성한 VECTOR_DIR만 로드한다는 전제(신뢰 소스)
    _store = FAISS.load_local(
        str(out_dir), get_embeddings(), allow_dangerous_deserialization=True
    )
    return _store
RAG 단계언제핵심 연산비용
인덱싱(build_index)사전 1회 · 문서 변경 시청킹 → 임베딩 → save_local비쌈(전체 임베딩)
로드(get_store)서버 기동 1회load_local → 캐시중간(재임베딩 없음)
검색(search)요청마다질문 임베딩 → 유사도 top_k쌈
증분(add_documents)새 문서 도착 시새 청크만 임베딩 → 추가쌈(신규분만)

배운 점"요청마다 재인덱싱"의 유혹은 코드가 단순해서 온다 — 한 함수에서 로드·검색을 다 하면 되니까. 하지만 그건 매 질문에 전체 문서를 다시 임베딩하는 꼴이라 상품·정책이 수백 건이면 답이 느려터진다. 인덱싱(1회)과 서비스(로드)를 물리적으로 build_index.py ↔ service.py로 갈라 두니, "비싼 건 미리 한 번, 요청 때는 검색만"이 구조로 강제됐다.

CH 04검색의 함정 — 점수는 거리다#

검색 함수는 질문 하나를 임베딩해 가까운 청크를 top_k만큼 돌려준다. 여기서 실측으로 데인 함정이 있었다 — FAISS의 similarity_search_with_score가 돌려주는 점수는 유사도가 아니라 거리다. 즉 작을수록 유사하다. 코사인 유사도(클수록 유사)와 정반대라 정렬·임계값 로직에서 부호를 뒤집는 실수가 나기 쉽다. 그래서 반환 필드명 자체를 distance로 못박아 헷갈림을 원천 차단했다.

def search(query, k=None, source=None):
    k = k or settings.RAG_TOP_K                             # 기본 top_k = 3
    store = get_store()
    filter_arg = {"source": source} if source else None
    pairs = store.similarity_search_with_score(query, k=k, filter=filter_arg)
    return [
        {
            "text": doc.page_content,
            "source": doc.metadata.get("source", ""),
            "distance": float(score),                       # 거리: 작을수록 유사(유사도 아님)
        }
        for doc, score in pairs
        if float(score) <= settings.RAG_MAX_DISTANCE        # 무관한 결과는 방어적으로 제외
    ]

의문top_k는 "가장 가까운 k개"인데, 문서에 답이 아예 없는 질문("오늘 날씨 어때?")을 던져도 벡터DB는 무조건 가장 가까운 3개를 돌려준다. 그럼 전혀 무관한 문단이 프롬프트에 실려 LLM이 엉뚱한 근거로 답하는 것 아닌가?

맞다 — 그래서 RAG_MAX_DISTANCE 임계값을 뒀다. 거리가 이 값(1.5)을 넘는 결과는 "무관"으로 보고 잘라낸다. 이게 의미를 가지려면 CH02에서 임베딩을 normalize=True로 정규화해 거리를 유계로 만들어 둔 것이 전제였다. Codex 구현 점검에서도 "무관 질의도 top-k를 반환한다"가 지적됐고, 정규화 + 임계값으로 무관 질의는 빈 리스트가 나오도록 고쳤다.

배운 점실제 라이브 검증에서 "ReAct 에이전트 무한루프 방지" 질의를 던지니 loop_safety.txt가 1순위(거리 순 정렬)로 정확히 잡혔다. "점수=거리(작을수록 유사)"와 "임계값으로 무관 결과 컷"은 표에서 읽을 땐 사소해 보였지만, 부호를 반대로 알면 가장 무관한 문서를 top으로 뽑는 조용한 버그가 된다. 공략집이 이걸 "반드시 기억할 함정"으로 따로 뽑아둔 이유를 코드로 납득했다.

CH 05메타필터·증분 업데이트 — FAISS vs Chroma#

실무 RAG에서 두 가지가 더 필요했다. 하나는 메타데이터 필터 — "멤버십 정책 안에서만 찾아줘"처럼 특정 문서로 검색 범위를 좁혀 노이즈를 줄인다. 다른 하나는 증분 업데이트 — 새 상품 매뉴얼이 하나 추가됐다고 전체를 재빌드하지 않고 새 청크만 임베딩해 붙인다. 통합 앱의 add_documents는 build_index와 같은 splitter를 재사용해 청킹 후 추가하고 다시 저장한다(원문을 통째로 넣으면 긴 문서 검색 품질이 떨어지므로).

이 두 요구가 FAISS와 Chroma의 선택 기준을 갈랐다. 실습에서 둘을 다 만져본 뒤 정리한 대비는 이렇다.

항목FAISSChroma
성격가볍고 빠른 벡터 검색 라이브러리메타필터·컬렉션 관리 편한 임베디드 벡터DB
영속화save_local/load_local(index.faiss+pkl)persist_directory
메타필터가능(filter=)편리 — filter={"source": ...}
적합복잡한 필터 없는 대부분의 RAG특정 문서만 검색·필터 라우팅
 
# 실습(vector_db_pycharm_project) — 증분 업데이트: 새 청크만 임베딩해 붙인다
vs2 = FAISS.load_local(str(FAISS_DIR), emb, allow_dangerous_deserialization=True)
new_chunks = load_and_chunk(["멤버십정책.txt"])   # 새로 도착한 문서만
vs2.add_documents(new_chunks)                       # 기존 문서는 재임베딩하지 않음
vs2.save_local(str(FAISS_DIR))
# → "환불은 며칠?" 같은 기존 지식 검색도 그대로 유지됨을 실측 확인

배운 점통합 앱은 필터가 단순(source 파일명 정도)이라 FAISS로 충분했고, 실습에서는 메타필터가 핵심인 케이스를 Chroma로 따로 만져봤다. 판단 기준이 "무엇이 더 좋은가"가 아니라 "메타데이터 필터·라우팅이 얼마나 중요한가"라는 걸 두 코드를 직접 돌려보고서야 잡았다. 증분 업데이트가 왜 "새 청크만"이 중요한지도 — 전체 재임베딩을 피해 비용·시간을 아끼는 게 곧 인덱싱/서비스 분리와 같은 정신이었다.

CH 06LangChain으로 묶기 — RAG를 에이전트의 도구로#

여기까지가 RAG의 원리를 손으로 배운 부분이다. LangChain은 이 원리들(문서 로더·splitter·임베딩·벡터스토어·도구 등록)을 표준 인터페이스로 자동화하는 프레임워크다. 실제로 오늘 코드는 이미 LangChain 위에 있었다 — RecursiveCharacterTextSplitter, HuggingFaceEmbeddings, FAISS 벡터스토어가 전부 LangChain 컴포넌트다. 마지막 조각은 이 RAG 검색을 에이전트가 스스로 호출하는 도구 한 개로 노출하는 것이었다.

통합 커머스 에이전트는 도구 6종(가격·재고·주문·상품검색·환율·지식검색)을 쓰는데, 그 여섯 번째가 오늘 만든 RAG다. LangChain @tool로 감싸 search_knowledge_base라는 이름과 설명만 주면, 에이전트가 "정책·매뉴얼 질문이면 이 도구를 부른다"고 스스로 판단한다.

from langchain_core.tools import tool

@tool
def search_knowledge_base(query: str) -> str:
    """정책·매뉴얼 등 지식 문서를 검색한다(RAG). 인자: query(자연어 질문)."""
    return _dumps(C.search_knowledge_base(db, query))       # 내부에서 rag.service.search 호출

도구 내부는 앞 장에서 만든 search()를 그대로 부른다 — 즉 CH03~04의 "로드된 인덱스에서 거리 순 top_k 검색"이 에이전트의 한 액션으로 승격된 것이다. LangChain은 여기서 더 나아가 create_agent(llm, tools, system_prompt) 한 줄로 ReAct 루프를, 긴 PDF는 청크별 요약(map) 후 통합(reduce)하는 map-reduce 요약까지 표준화해 준다(이건 다음 단원 주제로 예고).

def search_knowledge_base(db, query: str) -> dict:
    from app.rag.service import search
    results = search(query)                                  # CH03~04의 검색 그대로
    return {"ok": True, "count": len(results), "results": results}

배운 점오늘 잡은 전체 그림. 문서 → 청킹·임베딩(9주차 임베딩의 문장 확장) → FAISS 인덱스로 저장(인덱싱/서비스 분리) → 질문 임베딩 → 거리 순 top_k 검색(점수=거리 함정) → 임계값으로 무관 컷 → 그 결과를 LangChain @tool로 감싸 에이전트에 연결. 지난 LLM 글의 "환각을 줄이려면 외부 데이터와 연결하라"가 이제 실행되는 도구 한 개로 손에 잡혔다. 다음은 이 도구를 에이전트가 다른 도구들과 조합해 자율적으로 쓰는 ReAct 통합으로 이어진다.
