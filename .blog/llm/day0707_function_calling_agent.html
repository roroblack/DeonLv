LLM은 텍스트를 생성하는 모델인데, 어떻게 우리 DB의 재고를 조회하고 함수를 실행한다는 건가? 모델이 파이썬 코드를 실행할 리는 없다. 오늘 그 빈칸을 통합 커머스 에이전트(_unified_mall_agent_project)의 실제 도구·루프 코드로 메운다. 핵심은 처음부터 하나였다 — 결정과 실행의 분리. 모델은 "무엇을 부를지" JSON으로 결정만 하고, 실제 실행은 우리 코드가 한다. 이 한 문장이 도구 설계와 ReAct 루프 전체를 관통한다.

CH 01Function Calling — 실행하지 않고 결정만 한다#

Function Calling(함수 호출)은 LLM이 함수를 직접 실행하는 게 아니라, "어떤 함수를 어떤 인자로 부를지"를 JSON으로 결정하는 것이다. 실제 실행은 우리 파이썬 코드가 한다. 이게 LLM을 외부 세계(DB·API)와 잇는 다리이자, 환각을 막고 실시간 사실을 조회하는 핵심 메커니즘 — 에이전트의 "손발"이다.

의문LLM은 텍스트 생성 모델인데, "함수를 호출한다"는 말이 성립하나? 모델이 우리 서버의 get_price()를 실제로 실행할 리는 없을 텐데, 그럼 정확히 무엇이 오가는 건가.

오가는 것은 스키마와 tool_call이다. 우리는 모델에게 "이런 도구들이 있다"고 각 함수의 이름·설명·인자 스펙을 JSON 스키마로 미리 알려준다. 커머스 에이전트는 도구 6종을 OpenAI function-calling 형식으로 선언했다. 반복되는 골격은 헬퍼로 묶어, 이름·설명·인자 하나씩만 넘기면 스키마가 찍혀 나온다.

def _schema(name: str, desc: str, prop: str, prop_desc: str) -> dict[str, Any]:
    return {
        "type": "function",
        "function": {
            "name": name,
            "description": desc,                       # 모델이 읽는 '도구 설명'
            "parameters": {
                "type": "object",
                "properties": {prop: {"type": "string", "description": prop_desc}},
                "required": [prop],
            },
        },
    }

# OpenAI function-calling 스키마 (도구 6종)
TOOLS_SCHEMA = [
    _schema("get_price", "상품 코드로 가격 조회", "product_code", "상품 코드 예: P0001"),
    _schema("get_stock", "상품 코드로 재고/재주문 필요 조회", "product_code", "상품 코드"),
    _schema("get_order_status", "주문번호로 상태/금액 조회", "order_no", "주문번호"),
    _schema("search_product", "상품명 키워드 검색", "keyword", "검색 키워드"),
    _schema("get_exchange_rate", "통화 환율 조회", "currency", "USD/EUR/JPY"),
    _schema("search_knowledge_base", "정책·매뉴얼 지식 문서 검색(RAG)", "query", "자연어 질문"),
]

모델은 이 스키마를 보고, 질문에 맞는 도구를 골라 tool_calls(함수명 + 인자 JSON)를 반환한다. 예컨대 "P0001 가격 알려줘"에는 예시로 이런 결정을 내린다 — {"name": "get_price", "arguments": {"product_code": "P0001"}}. 여기서 끝이 아니다. 이건 결정일 뿐, 실제 조회는 아직 안 됐다.

배운 점의문이 여기서 풀렸다. 오가는 건 함수의 실행이 아니라 실행 지시(JSON)다. 흐름은 이렇다 — ① 우리가 스키마로 도구 목록을 알려줌 → ② 모델이 tool_call(어떤 함수·어떤 인자)을 JSON으로 반환 → ③ 우리 코드가 실제 함수를 실행 → ④ 결과를 tool 메시지로 되돌림 → ⑤ 모델이 그 결과를 보고 최종 답을 생성. SDK가 ③까지 자동으로 해주는 자동 FC도 있지만, 오늘은 원리를 손에 잡으려 이 루프를 수동으로 짰다. 모델이 함수를 실행한다는 착각이, "모델은 결정하고 코드가 실행한다"로 바로잡히는 순간이다.

CH 02좋은 도구 5원칙 — 모델은 함수 본문을 못 본다#

스키마를 에서 분명하게 깨달은 게 있다. 모델에게 전달되는 건 함수의 이름·인자·설명(독스트링)뿐, 함수 본문은 가지 않는다. 즉 모델이 도구를 고르는 근거는 오직 그 메타정보다. 그래서 독스트링은 주석이 아니라 모델용 프롬프트다. 커머스 도구는 이 감각으로 짠 좋은 도구 5원칙을 따른다.

원칙의미커머스 도구에서
① 한 가지 일만도구 하나 = 책임 하나가격·재고·주문을 각각 별도 도구로
② 이름 = 기능이름만 봐도 무엇인지get_price, get_stock
③ 명확한 인자타입·형식을 스펙에product_code(예: 'P0001')
④ 구체적 독스트링모델이 읽는 설명"상품 코드로 가격을 조회한다. 인자: …"
⑤ 일관된 반환항상 같은 구조로모든 도구가 dict 반환
 
def get_stock(db: Session, product_code: str) -> dict[str, Any]:
    """상품 코드로 재고와 재주문 필요 여부를 조회한다. 인자: product_code."""
    product = db.query(Product).filter(Product.product_code == product_code).first()
    if product is None:
        return _fail("product_not_found", f"상품을 찾을 수 없습니다: {product_code}")
    inv = db.query(Inventory).filter(Inventory.product_id == product.id).first()
    stock = inv.stock if inv else 0
    reorder = inv.reorder_level if inv else 0
    return {
        "ok": True, "product_name": product.name,
        "stock": stock, "reorder_level": reorder,
        "need_reorder": stock <= reorder,     # 판단까지 도구가 계산해 넘긴다
    }

정리특히 유사 도구 구분이 실전 포인트였다. get_price(정확한 코드로 1건)와 search_product(키워드로 여러 건)는 하는 일이 비슷해 모델이 헷갈릴 수 있다. 그래서 독스트링에 입력 형태(코드 vs 키워드)와 반환 건수(1건 vs 목록)를 못 박아 구분한다. "상품 코드로"와 "상품명 키워드로"라는 한 구절 차이가, 모델이 옳은 도구를 고르게 하는 프롬프트가 된다. 함수를 짜는 게 아니라 모델이 읽을 설명서를 짜는 감각이다.

CH 03도구 오류 처리 — 삼키지 말고 관찰로 되돌린다#

도구가 실패하면 어떻게 되나. 없는 상품을 조회하면? 여기서 개념을 명확히 나눠야 했다. 실패에는 두 종류가 있다 — 예상된 비즈니스 실패(없는 상품·주문 등)와, 예상 밖 인프라 실패(DB 다운·LLM 서버 연결 끊김)다. 둘을 같이 다루면 에이전트가 엉뚱하게 멈추거나, 반대로 진짜 장애를 숨긴다.

의문도구 안에서 예외가 나면 try/except로 다 잡아서 "실패했어요"로 돌려주면 깔끔하지 않나? 왜 어떤 건 잡고 어떤 건 그대로 터뜨려야 한다는 건가.

원칙은 이랬다. 비즈니스 실패는 구조화된 실패 관찰({ok: false, error_code, message})로 바꿔 모델에 되돌린다 — 그래야 에이전트가 멈추지 않고 "그 상품은 없습니다"로 사과하거나 다른 도구를 시도한다. 반면 인프라 실패는 삼키지 않고 그대로 전파한다 — 정상 결과로 위장하면 진짜 장애가 묻히기 때문이다.

def _fail(code: str, message: str) -> dict[str, Any]:
    return {"ok": False, "error_code": code, "message": message}

def get_price(db: Session, product_code: str) -> dict[str, Any]:
    """상품 코드로 가격을 조회한다. 인자: product_code(예: 'P0001')."""
    product = db.query(Product).filter(Product.product_code == product_code).first()
    if product is None:
        # 비즈니스 실패 → 구조화 관찰(에이전트가 멈추지 않도록)
        return _fail("product_not_found", f"상품을 찾을 수 없습니다: {product_code}")
    return {"ok": True, "product_name": product.name, "price": product.price}

배운 점구현하며 하나 더 배운 게 있다. Phase 3 리뷰에서, 모델이 유효한 JSON이지만 인자 개수가 안 맞는 tool_call을 뱉으면 fn(db, **args)가 TypeError로 크래시하는 버그가 잡혔다. 여기서도 원칙이 갈렸다 — 잘못된 인자는 모델 탓이니 TypeError만 잡아 bad_arguments 관찰로 되돌리고(모델이 고쳐 다시 시도), 그 외 예외(InfraError 등)는 계속 전파. "실패를 어떻게 분류하느냐"가 곧 에이전트의 견고함이라는 걸, 개념이 아니라 잡힌 버그로 배웠다.

CH 04ReAct 루프 — Thought → Action → Observation#

도구가 준비됐으니 이제 루프다. 단발성 "AI 앱"과 "AI 에이전트"의 차이는 하나 — 누가 다음 행동을 결정하는가. 에이전트는 스스로 결정하고 반복한다. 그 반복이 ReAct(Reason + Act) 루프다. 생각(Thought)하고 → 도구를 실행(Action)하고 → 결과를 관찰(Observation)하고 → 다시 생각. 핵심은 관찰을 모델에 되돌리는 것이다. 도구 결과를 tool 메시지로 대화에 다시 넣어야 모델이 그걸 근거로 다음을 결정한다.

커머스 에이전트의 수동 루프는 이 사이클을 max_steps만큼 돈다. 모델이 tool_call을 반환하면 실행해 관찰을 append하고, tool_call 없이 답만 내면 그게 최종 답변이라 루프를 끝낸다.

for step_no in range(1, max_steps + 1):
    messages = _trim(messages)                       # 히스토리 트리밍(CH05)
    assistant = chat_fn(messages, TOOLS_SCHEMA)       # 모델에게 결정을 요청
    # assistant 메시지를 tool 결과보다 먼저 append (OpenAI 메시지 순서)
    messages.append(_assistant_to_openai(assistant))

    tool_calls = assistant.get("tool_calls")
    if not tool_calls:                                # 도구 호출이 없으면 = 최종 답변
        return AgentResponse(answer=assistant.get("content") or "",
                             steps=steps, stopped_by="final_answer")

    for tc in tool_calls:
        name, args = tc["name"], json.loads(tc["arguments"])
        fn = TOOL_MAP.get(name)
        observation = fn(db, **args)                  # 실제 실행 = 우리 코드
        messages.append(_tool_message(tc["id"], observation))   # 관찰을 되돌림
        steps.append(AgentStep(step=step_no, action=name,
                               action_input=args, observation=observation))

정리이 루프가 CH01~03을 한 줄로 꿴다. 모델이 tool_call을 결정(CH01) → 우리가 고른 도구를 실행(CH02) → 성공이든 구조화 실패든 관찰로 되돌림(CH03) → 모델이 그걸 보고 다음 결정. 하나 놓치기 쉬운 디테일은 메시지 순서 — OpenAI 형식은 assistant(tool_call 담은) 메시지를 먼저 넣고, 그 뒤에 각 tool_call_id에 대응하는 tool 메시지를 넣어야 짝이 맞는다. 순서가 틀리면 API가 거부한다. 원리는 단순하지만, 대화 배열을 손으로 조립하다 보면 이런 규약이 곧 버그의 온상이다.

CH 05루프의 안전장치 3종#

루프에는 반드시 브레이크가 필요하다. LLM은 같은 도구를 무한히 부르거나, 대화가 길어지며 토큰을 폭주시킬 수 있다. 커머스 에이전트의 수동 루프는 안전장치 3종을 뒀다.

안전장치막는 것구현
① max_steps무한 루프for step_no in range(1, max_steps+1)
② 중복 호출 차단같은 도구·인자 반복(도구명+인자) 서명을 set에 기록
③ 히스토리 트리밍토큰 폭주첫 질문(head) + 최근 N개(tail) 보존
 
def _signature(name: str, args: dict) -> str:
    return f"{name}:{json.dumps(args, sort_keys=True, ensure_ascii=False)}"

# 루프 안에서 — 같은 (도구, 인자) 조합이 다시 오면 무한루프로 보고 종료
sig = _signature(name, args)
if sig in seen:
    return AgentResponse(
        answer="동일한 도구와 인자가 반복 호출되어 무한루프 방지 장치가 작동했습니다.",
        steps=steps, stopped_by="duplicate_tool_call")
seen.add(sig)

③ 트리밍은 미묘한 함정이 있었다. 그냥 최근 N개만 남기면 tool 메시지가 짝이 되는 assistant(tool_call) 메시지를 잃어버려 API가 거부한다. 그래서 tail이 tool로 시작하면 앞 메시지를 하나 더 끌어와 짝을 맞춘다.

def _trim(messages: list[dict], keep: int = 8) -> list[dict]:
    """head(system+user) + 최근 keep개. tail이 tool로 시작하면 짝을 안 깨게 보정."""
    if len(messages) <= keep + 2:
        return messages
    head, tail = messages[:2], messages[-keep:]
    while tail and tail[0].get("role") == "tool":     # 짝 잃은 tool → 하나 더 포함
        tail = messages[-(len(tail) + 1):]
        if len(tail) >= len(messages) - 2:
            break
    return head + tail

배운 점세 장치 모두 결정론적으로 검증했다. 이게 설계의 또 다른 핵심이었다 — 루프는 chat_fn(모델 호출 함수)을 주입받게 짜여, 실제 LLM 없이 mock 결정으로 테스트한다. 정상 흐름(도구→관찰→최종답변), max_steps 종료, 중복 차단, 잘못된 인자 관찰까지 모델 없이 재현했다(테스트 통과). 라이브로는 로컬 Gemma가 OpenAI 네이티브 tool_calls를 반환하지 않는 제약이 확인돼(유사 tool-call을 텍스트로 뱉음), 루프 로직은 mock으로 검증하고 실제 tool-calling 검증은 최종 실키(OpenAI/Gemini)로 이관했다. "모델이 없어도 루프의 옳음을 증명할 수 있게" 만든 설계가, 불안정한 LLM에 의존하지 않고 견고함을 담보한 셈이다.

CH 06Planning — 계획으로 쪼개고, 틀리면 다시 세운다#

ReAct는 매 단계 즉흥적으로 다음 행동을 결정한다. 반대 접근이 Plan-and-Execute — 미리 전체 계획을 세우고 실행한다. 큰 목표는 하위 단계로 분해하는 게 유리하다. 커머스 에이전트는 with_structured_output(Plan)으로 계획을 Pydantic 객체로 강제했다. 자유 텍스트가 아니라 구조를 강제해야 검증할 수 있기 때문이다.

class Plan(BaseModel):
    goal: str = Field(description="달성할 목표")
    steps: list[str] = Field(description="목표를 이루기 위한 순차 단계")

def validate_plan(plan: Plan) -> list[str]:
    """계획의 문제점 목록을 반환한다(빈 리스트 = 유효). 예외를 던지지 않는다."""
    problems: list[str] = []
    n = len(plan.steps)
    if n < MIN_STEPS: problems.append(f"단계가 너무 적습니다({n} < {MIN_STEPS}).")
    if n > MAX_STEPS: problems.append(f"단계가 너무 많습니다({n} > {MAX_STEPS}).")
    if any(not (s and s.strip()) for s in plan.steps):
        problems.append("빈 단계가 있습니다.")
    return problems

계획이 검증에 실패하면? 여기서 재계획(replan) 루프가 돈다. 실패 사유를 모델에 피드백해 다시 분해시키고, 정해진 횟수만큼 재시도한다. CH03의 오류 철학이 여기서도 반복된다 — 실패를 조용히 삼키는 폴백이 아니라, 재시도 후에도 안 되면 LLMOutputError로 노출한다.

def plan_with_validation(goal, make=None, remake=None, max_replan=2) -> Plan:
    """생성→검증→(실패 시)재계획 루프. 초과 후에도 실패면 LLMOutputError."""
    plan, problems = _attempt(lambda: make(goal))
    attempts = 0
    while problems and attempts < max_replan:          # 실패 사유를 피드백해 재계획
        attempts += 1
        reason = "; ".join(problems)
        plan, problems = _attempt(lambda: remake(goal, reason))
    if problems:
        raise LLMOutputError(f"유효한 계획 생성 실패(재계획 {attempts}회): {problems}")
    return plan

배운 점오늘 잡은 그림은 이렇다. LLM(두뇌)에 도구(Function Calling, 결정과 실행의 분리)를 붙이고, 그 도구들을 모델이 고를 수 있게 이름·독스트링으로 설계하고(5원칙), 실패를 구조화 관찰로 다루고(비즈니스 vs 인프라), 이 셋을 ReAct 루프로 반복하되 안전장치 3종으로 폭주를 막고, 큰 목표는 구조화 계획으로 쪼개 검증·재계획한다. 지난 글에서 "환각을 막으려면 외부 데이터와 연결하라"고 예고만 했던 그 연결이, 오늘 도구·루프·계획이라는 구체적 설계로 손에 잡혔다. 다음은 이 에이전트의 지식 도구(search_knowledge_base)를 채울 RAG로 이어진다 — 커머스 에이전트가 정책·매뉴얼까지 근거로 답하게 하는 마지막 조각이다.
