여기까지 딥러닝 단원에서 RNN·LSTM의 정보 병목을 봤고, 어텐션과 트랜스포머로 "순서를 버리고 문장 전체 관계를 한 번에 읽는" 구조까지 왔다. 그런데 강의 노트를 되짚다 계속 걸린 지점이 있었다. 트랜스포머는 구조일 뿐인데, 어떻게 그게 번역·요약·코드작성을 한꺼번에 하는 하나의 제품이 된 걸까. 오늘은 그 빈칸 — 구조에서 LLM으로 — 을 두 방향에서 메운다. 개념(사전학습·스케일)으로 한 번, 그리고 BERT를 직접 파인튜닝한 실습으로 다시 한 번. "파운데이션 모델을 가져와 우리 과제에 맞춘다"는 LLM 시대의 패러다임을 축소판으로 손에 잡아보는 것이 오늘의 목표였다.

CH 01LLM이란 무엇인가#

LLM은 Large Language Model, 대규모 언어 모델이다. 강의는 그 상징으로 2020년 공개된 GPT-3를 든다. 1,750억 개 파라미터를 가진 자기회귀(auto-regressive) 언어 모델로, 여기서 자기회귀란 앞의 토큰들을 보고 다음 토큰을 예측하는 방식을 뜻한다. 지난 언어 모델 글에서 LSTM이 다음 단어를 확률로 맞추던 그 원리가, 트랜스포머 위에서 대규모로 반복된 것이다.

의문노트를 정리하며 막혔던 질문. 트랜스포머는 Attention Is All You Need에서 본 '아키텍처'인데, 그 구조 자체가 어떻게 질문답변·번역·요약을 다 하는 하나의 모델이 되나? 구조와 능력 사이에 뭐가 채워진 건가.

강의가 채워준 빈칸은 사전학습(Pre-training)과 스케일(scale)이었다. 사전학습은 LLM을 만들 때 가장 먼저 하는 대규모 학습 단계로, 인터넷 문서·책·코드·위키 같은 방대한 텍스트에서 오직 "다음 토큰 맞추기"만 반복한다. 입력이 "인공지능은 데이터를 학습하여"라면 정답은 "패턴" 같은 식이다. 이 단순한 과제를 거대한 데이터로 충분히 반복하면 모델은 문장 구조, 단어 의미 관계, 문맥, 상식적 표현, 코드 패턴, 질문-답변 구조까지 부수적으로 습득한다. 즉 사전학습은 언어의 기본 능력을 통째로 갖추는 과정이다.

배운 점GPT-3가 준 진짜 메시지는 성능 수치가 아니라 "모델 크기를 크게 키우면 별도의 세부 학습 없이도 여러 작업을 수행한다"는 관찰이었다. 기존 NLP는 감성분석·번역·요약·질의응답을 작업마다 따로 학습시켜야 했다. LLM 이후로는 하나의 모델이 프롬프트만 바꿔 여러 작업을 처리한다. 트랜스포머라는 '구조'가 '제품'이 된 지점이 바로 여기 — 스케일이 붙은 사전학습이었다. 그렇다면 그 "따로 학습시키던" 옛 방식은 실제로 어떻게 하는가. 다음 장에서 직접 돌려봤다.

CH 02파인튜닝을 직접 해보다 — BERT/KoELECTRA 전이학습#

스케일이 붙기 전, 그리고 지금도 특화 작업에서 쓰이는 방식이 파인튜닝(Fine-tuning, 전이학습)이다. 대량 데이터로 미리 학습된 모델을 가져와, 우리 과제(감성분석)에 맞게 일부만 재학습하는 것 — "밑바닥부터 학습"보다 훨씬 적은 데이터로 높은 성능을 낸다. LLM 시대의 "파운데이션 모델 + 특화" 패러다임을 그대로 축소한 형태다. 개념만 읽으면 뜬구름 같아, Bert_sentiment_project로 리뷰 감성분석(긍정/부정) 파인튜닝을 직접 돌렸다.

구조는 사전학습 백본 위에 분류 헤드(Linear Layer)를 얹는 형태다. 영어는 bert-base-uncased + BertForSequenceClassification, 한국어는 KoELECTRA(monologg/koelectra-base-v3-discriminator) + AutoModelForSequenceClassification을 백본으로 썼다. 입력은 토크나이저가 [CLS]·[SEP] 등 특수 토큰을 붙이고 max_len(한국어 64, 영어 128)에 맞춰 자르거나 padding으로 채운다. 실제 모델 로드 코드는 이렇게 짧다.

from transformers import AutoModelForSequenceClassification

def create_model(model_name: str, num_labels: int = 2):
    # 백본(사전학습) 위에 분류 헤드를 붙여 준다.
    # 헤드가 없거나 크기가 다르면 새로 초기화되도록 옵션을 둔다.
    model = AutoModelForSequenceClassification.from_pretrained(
        model_name,
        num_labels=num_labels,          # 긍정/부정 2분류
        ignore_mismatched_sizes=True,
    )
    return model

의문전이학습이라면서 "일부만 재학습"이라는데, 그 일부를 실제로 어떻게 지정하나? 1억 개가 넘는 파라미터 중 뭘 얼리고 뭘 학습시킬지 코드로는 어떻게 표현되는가.

답은 레이어 동결(freeze) 전략이었다. requires_grad 플래그를 켜고 끄는 것으로, 어느 파라미터에 그래디언트를 흘릴지 정한다. 이 프로젝트는 네 가지 전략을 두었다.

전략학습 범위성격
0전체 파라미터 (풀 파인튜닝)가장 정확하지만 가장 느림
1백본 전체 동결 · 분류 헤드만 학습가장 빠르지만 표현력 낮음
2pooler + 분류 헤드만 학습절충(하)
3마지막 인코더 레이어 + pooler + 분류 헤드절충(상), 기본값
 
# 전략 3 — 마지막 인코더 레이어와 pooler만 남기고 백본을 동결
for name, param in backbone_params:              # classifier는 항상 학습
    keep = ("pooler" in name) or (last_layer_tag in name)
    if not keep:
        param.requires_grad = False              # 그래디언트 차단 = 동결

학습은 HuggingFace Trainer + TrainingArguments로 묶고, compute_metrics에서 accuracy·precision·recall·f1을 함께 뽑았다. 한국어는 NSMC(Naver sentiment movie corpus)를 자동으로 내려받아 백본을 파인튜닝했다. 여기서 실제로 돌린 두 실험의 실측값이 개념을 확 잡아줬다.

학습 가능 파라미터7.68M / 112.9M (6.8%)112.9M / 112.9M (100%)
학습 표본 · Epoch6,000 · 18,000 · 1

배운 점부분학습(전략 3)은 전체의 6.8%만 학습해 빠른 대신, 백본 대부분이 얼어붙어 과소적합됐다 — 학습 도메인(영화 리뷰)과 다른 일반 문장에서 모두 '긍정'으로 치우쳤다(6개 중 3개만 정답). 백본 전체를 푼 전략 0에서 정확도가 75.6% → 87.1%로 오르고 편향도 사라졌다. 더 큰 독립 표본(NSMC 공식 테스트 5,000개)으로는 84.3%가 일반화 성능에 가까운 값이었다. 참고로 NSMC 전체(15만)로 학습된 공개 사전학습 모델(monologg/koelectra-base-finetuned-nsmc)은 같은 5,000개에서 90.0%였다 — "데이터·학습량을 늘릴수록 근접한다"는 감을 숫자로 확인한 셈이다. 무엇을 얼리고 무엇을 학습시키느냐가 곧 성능·시간의 trade-off라는 것을, 표가 아니라 내 로그로 봤다.

이 실습이 채워준 빈칸은 컸다. 트랜스포머(구조) → 사전학습된 BERT/KoELECTRA(백본) → 분류 헤드를 붙여 우리 데이터로 미세조정(파인튜닝) → 감성분석기(제품). 여기에 "작업마다 따로 학습"이 아니라 "하나로 프롬프트만 바꿔"가 붙으면 다음 장의 LLM이 된다. 같은 전이학습 사고를, GPT는 사전학습 규모로 대체했을 뿐이다.

CH 03모델의 종류와 재학습 없이 쓰는 법#

LLM은 하나로 뭉뚱그려지지만 구조와 목적에 따라 갈린다. 앞선 논문 글에서 본 GPT 계열(생성)과 BERT 계열(이해)의 분기가 여기서 종류표로 정리됐다. 방금 파인튜닝한 KoELECTRA·BERT가 바로 아래 Encoder-only 칸의 "이해" 모델이다.

종류설명예시
Decoder-only이전 토큰을 보고 다음 토큰을 생성GPT 계열
Encoder-only문장을 이해하고 분류하는 데 강함BERT · ELECTRA 계열
Encoder-Decoder입력 문장을 다른 문장으로 변환T5, BART
Instruction-tuned사람의 지시를 잘 따르도록 추가 학습InstructGPT, ChatGPT 계열
Multimodal텍스트뿐 아니라 이미지·음성 등도 처리GPT-4o 계열

GPT 계열은 글쓰기·답변·코드작성·요약·번역·챗봇처럼 생성형 작업에, BERT 계열은 문장분류·감성분석·개체명 인식·유사도·검색 랭킹처럼 이해 기반 작업에 강하다. 즉 지난 임베딩 글에서 짚은 "고정 임베딩 → 문맥 임베딩(BERT/GPT)"의 두 갈래가, 그대로 오늘의 두 모델 계열로 이어진다. 방금 CH02에서 이해 계열 하나를 직접 파인튜닝한 셈이다.

그런데 여기서 특히 궁금했던 건, CH02에서 한 파인튜닝과의 관계였다. 작업마다 모델을 그렇게 다시 학습시키지 않는다면, 실제로는 어떻게 원하는 작업을 시키는가?

정리In-context Learning이 그 답이다. 모델을 다시 학습(파인튜닝)시키지 않고, 프롬프트 안에 설명이나 예시를 넣어 원하는 작업을 시키는 방식이다. 예컨대 "다음 문장의 감성을 긍정/부정으로 분류하라"는 지시에 예시 문장 두어 개를 붙이면, 모델은 그 패턴을 보고 마지막 문장의 답을 생성한다. CH02에서는 감성분석기를 만들려고 데이터셋을 모아 25분을 학습시켰지만, 충분히 큰 LLM은 같은 분류를 프롬프트 예시 몇 줄로 해낸다. 별도 학습 데이터셋도, 재학습도 필요 없다 — 사전학습으로 얻은 범용 능력을 프롬프트로 '지시'만 하는 것이다.

CH 04프롬프트와 예시 개수, 그리고 환각#

프롬프트(Prompt)는 LLM에게 전달하는 입력 지시문이다. 단순 질문일 수도, 역할·조건·출력 형식을 담은 상세 명령일 수도 있다. 강의의 대비가 인상적이었다. 나쁜 프롬프트는 "LLM 설명해줘." 한 줄이고, 좋은 프롬프트는 "너는 인공지능 강사이다. LLM의 개념을 … 정의·학습 방식·Transformer 구조·API 활용·실무 사례를 포함해 설명하라"처럼 역할과 항목을 지정한다. 프롬프트 품질이 답변 품질을 좌우한다.

In-context Learning은 예시를 몇 개 주느냐로 세 갈래가 된다.

방식예시 개수특징
Zero-shot0개예시 없이 바로 지시
One-shot1개예시 하나로 답변 형식을 보여줌
Few-shot여러 개원하는 답변 패턴을 여러 개로 제시 → 결과가 더 안정적

배운 점지난 GPT-3 논문 글(Language Models are Few-Shot Learners)에서 본 제목의 의미가 여기서 맞물렸다. 강의도 같은 점을 짚는다 — 모델을 큰 규모로 확장하면 few-shot 성능이 크게 향상된다는 것. 예시를 주기만 해도 재학습 없이 새 작업을 배우는 이 능력 자체가 스케일의 산물이었다. CH02의 파인튜닝이 '가중치를 바꿔' 새 작업을 익혔다면, few-shot은 '가중치를 고정한 채 프롬프트로' 익힌다. '구조 → 사전학습 → 스케일 → few-shot'으로 흐름이 하나로 꿰였다.

다만 LLM은 만능이 아니다. 환각(Hallucination)은 사실이 아닌 내용을 그럴듯하게 생성하는 현상으로, 존재하지 않는 논문 제목이나 없는 API 함수, 출처 없는 통계를 자신 있게 지어낸다. 보완책은 RAG 적용, 공식 문서·DB 조회 기반 답변, 출처 표시, 검증 로직과 사람 검토 단계 추가 등이다. 핵심은 "LLM에게 전부 맡기지 말고 외부 데이터와 연결하라"는 것 — 사용자 질문 → 관련 문서 검색 → 검색된 문서를 LLM에 제공 → 근거 기반 답변, 이 구조가 RAG다. (RAG·Function Calling은 뒤 단원의 주제로 예고만.)

CH 05API로 부른다는 것 — 토큰과 컨텍스트#

API 방식은 Python·JavaScript·Streamlit 같은 프로그램에서 LLM 서버를 호출하는 방식이다. 기본 흐름은 사용자 입력 → 앱에서 API 요청 생성 → LLM 서버가 응답 생성 → 앱 화면에 출력. CH02의 파인튜닝 모델은 우리가 가중치를 쥐고 로컬에서 돌렸지만, API 모델은 가중치가 서버에 있고 우리는 호출만 한다는 점이 대비된다. 강의의 Python 예시를 개념용으로 옮기면 다음과 같다. 실제 실행 로그가 아니라 사용 형태를 보여주는 의사(擬似) 코드다 — 이 글에서는 API 키가 없어 호출하지 않았다.

import os
from openai import OpenAI

# API Key를 코드에 직접 쓰면 노출 위험이 있으므로 환경변수에서 읽는다
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

user_input = "LLM에서 zero-shot과 few-shot의 차이를 설명해줘."

# 모델에게 응답 생성을 요청한다 (개념용 — 실제 호출 아님)
response = client.responses.create(
    model="gpt-...",       # 사용할 LLM 모델 지정
    input=user_input,
)

print(response.output_text)  # 모델이 생성한 최종 텍스트

여기서 API를 이해하는 핵심 단위가 토큰(Token)이다. LLM은 문장을 토큰 단위로 읽고 생성하며, 과금도 대체로 토큰 사용량 기준이다. 토큰은 단어와 완전히 같지 않다 — 영어는 짧은 단어 단위로, 한국어는 조사·어절·부분 문자열 단위로 쪼개질 수 있다. 지난 전처리 글에서 BPE(Byte Pair Encoding) 서브워드 토큰화를 봤고, CH02에서도 토크나이저가 문장을 max_len까지 토큰 ID로 잘라 넣었다. 그 서브워드 결과물이, API에서는 그대로 비용의 단위가 된다.

의문토큰이 곧 비용이라면, "긴 대화를 이어가면" 무엇이 쌓이는 건가? 내가 보낸 질문만 계산되나, 아니면 이전 대화 전체가 매번 다시 들어가나?

토큰 유형무엇인가포함되는 것(예)
Input 토큰API에 보낸 모든 입력System·User 메시지, 예시, 검색된 문서, 이전 대화 기록, 코드·표
Output 토큰모델이 생성한 응답설명·코드·요약·번역·분석·JSON 결과
Cached 토큰이전 입력이 캐시되어 할인 적용될 수 있는 토큰반복되는 입력의 일부

배운 점의문의 답이 여기 있었다. 이전 대화 기록이 Input 토큰에 포함된다 — 즉 대화가 길어질수록 매 요청에 과거 맥락이 함께 실려 입력 토큰이 누적된다. 이것이 컨텍스트 윈도우(모델이 한 번에 다룰 수 있는 토큰 범위)를 관리해야 하는 이유다. 총 사용 토큰 = Input + Output이므로(예: 입력 1,000 + 출력 500 = 1,500), 비용 절감은 관련 없는 긴 문서 제거, 출력 길이 제한, 요약본 사용, RAG로 필요한 문단만 전달, 시스템 프롬프트 최소화로 이어진다. "좋은 프롬프트 · 정확한 외부 데이터 연결 · 토큰과 비용 관리" — 강의가 꼽은 실무 3요소다.

CH 06생성 제어 파라미터 — 창의성·후보·길이#

API 호출에는 답변의 성격을 조절하는 파라미터가 붙는다. 보조 강의자료가 꼽는 세 가지는 Temperature · Top P · Maximum Tokens로, 각각 생성의 창의성·후보 단어 범위·출력 길이를 제어한다. 앞서 본 "다음 토큰을 확률로 고른다"는 원리를 떠올리면 셋 다 그 확률 분포를 어떻게 다룰지에 대한 설정임이 보인다.

  • Temperature — 얼마나 다양한 단어를 고를지. 값이 낮을수록 확률이 가장 높은 단어를 우선 골라 답이 안정적·일관적이고, 높을수록 확률이 낮은 단어도 골라 표현이 다양·창의적이 된다.
  • Top P — 후보 단어의 범위를 누적 확률로 자른다(Nucleus Sampling). 값이 작으면 안정적인 단어만, 크면 다양한 단어까지 후보에 넣는다.
  • Maximum Tokens — 생성할 최대 출력 길이 제한. 작으면 짧고 빠르고 저렴, 크면 긴 설명이 가능하나 비용·응답시간이 는다.

Top P의 감이 잡히지 않았는데, 강의의 예가 명료했다. 다음 단어 확률이 사과 40% · 배 25% · 포도 15% · 딸기 10% … 라면, Top P = 0.5는 누적 50%까지인 {사과, 배}만 후보로 쓰고, Top P = 0.9는 누적 90%까지 넓혀 {사과, 배, 포도, 딸기}를 후보로 삼는다. 즉 "가장 유력한 답만 볼지, 여러 가능성을 함께 볼지"의 조절이다. CH02에서 KoELECTRA가 뱉은 긍정 0.8948 / 부정 0.1052 같은 확률 분포를, 생성 모델에서는 이 파라미터들로 다루는 셈이다.

# 파라미터를 함께 지정한 형태 (개념용 — 실제 호출 아님)
response = client.responses.create(
    model="gpt-...",
    input="LLM의 주요 파라미터를 설명해줘.",
    temperature=0.3,          # 안정적·일관성 있는 답변
    top_p=0.9,                # 누적 90% 후보에서 자연스러운 다양성
    max_output_tokens=500,    # 응답 길이·비용 제한
)
print(response.output_text)

배운 점세 파라미터는 결국 하나의 축으로 이어진다. 정확성이 중요하면 Temperature를 낮게, 창의성이 필요하면 높게. Top P를 함께 조절해 다양성을 세밀하게 다루고, Max Tokens로 길이와 비용까지 잡는다. 오늘 잡은 그림은 이렇다 — 트랜스포머(구조)를 사전학습해 백본(BERT/GPT)이 되고, 그 백본을 파인튜닝하면 특화 모델(CH02의 감성분석기)이, 규모를 키워 프롬프트로 지시하면 LLM이 된다. 그리고 그걸 API 한 줄로 부르되(토큰·컨텍스트), 파라미터로 답변의 성격을 조율한다. 다음은 이 두뇌에 도구·기억을 붙이는 에이전트와 RAG로 이어진다.
