LLM을 만드는 쪽에서 쓰는 쪽으로 — 11주차 회고

10주차가 "트랜스포머에서 LLM으로" 넘어가는 다리였다면, 11주차(0706~0710)는 LLM을 실제로 다루는 기술이었다. 출력을 제어하고(파라미터), 프롬프트를 설계하고(역할·few-shot·CoT), 도구를 붙이고(Function Calling·ReAct), 지식을 검색해 붙이고(RAG), 마지막에 그 모든 걸 하나의 쇼핑몰 에이전트로 통합했다. 한 줄 목표는 — "모델을 만드는 것에서, 모델을 잘 쓰는 것으로." 스테이지마다 전용 콘솔 실습으로 부품을 익힌 뒤 통합 프로젝트로 합쳤고, 코드·설계·측정값은 실제 프로젝트에서 인용한다.

CH 01출발 — 트랜스포머를 넘어, 쓰는 기술로#

지금까지는 모델을 만드는 쪽이었다 — 형태소로 자르고, 임베딩으로 벡터화하고, LSTM·트랜스포머를 학습시켰다. 11주차는 방향이 바뀌었다. 이미 학습된 거대한 LLM을 API로 가져다, 어떻게 원하는 대로 움직이게 할지가 과제였다.

의문 LLM은 프롬프트 한 줄이면 답을 준다. 그런데 왜 파라미터·도구·검색·에이전트 같은 층이 더 필요할까?
배운 점 프롬프트만으로는 출력의 일관성(파라미터)·최신 지식(RAG)·실제 행동(도구)을 보장할 수 없었다. 이 세 결핍이 이번 주의 세 챕터(제어·행동·지식)를 그대로 만들었고, 마지막에 하나로 합쳐졌다. (스테이지별 콘솔 실습 → 통합 프로젝트)
다음으로 — 먼저 출력을 원하는 모양으로 다듬는 제어부터.

CH 02제어 — 파라미터와 프롬프트 엔지니어링#

회수

0706엔 출력을 조율하는 두 손잡이를 익혔다. 파라미터(temperature·top-p로 다양성/일관성 조절)와 프롬프트 설계(역할·few-shot 예시·CoT 유도). 특히 분류처럼 정답이 하나면 temperature=0으로 고정하고, 헷갈리는 짝은 few-shot 경계 예시로 잡았다.

app/prompts · lab — 작업 유형별 실제 파라미터 사용
분류(classifier)   temperature=0    max_tokens=16    ← 정답 하나, 일관성 최우선
대화/생성          temperature=0.2  max_tokens=200   ← 약간의 다양성 허용
인젝션 방어        사용자 입력을 <<< … >>> 로 감싸 역할 지시와 분리
few-shot           오분류 짝(Counter)에서 경계 예시 자동 추천(suggest_fewshot_candidates)
배운 점 프롬프트는 "잘 부탁하기"가 아니라 설계였다 — 역할 고정, 경계 예시, 사용자 입력을 <<< >>>로 감싸는 인젝션 방어, 그리고 어려운 문제엔 단계적 추론(CoT)을 유도. 콘솔 실습(prompt_console·cot_console)으로 부품을 익혔다. (자세히: 파라미터·프롬프트 엔지니어링)
다음으로 — 제어된 출력을 넘어, LLM이 실제로 행동하게 하려면 도구가 필요했다.

CH 03행동 — Function Calling과 ReAct 루프#

회수

0707엔 LLM에 손발을 달았다. Function Calling으로 도구(재고 조회·가격 계산 등)의 스키마를 주면, LLM이 "어떤 도구를 어떤 인자로 부를지"를 정한다. 이걸 ReAct(Reason+Act) 루프로 감싸 — 생각→도구 호출→관찰→다시 생각 — 반복하게 했다.

app/agent/react.py + tools/commerce_tools.py — ReAct 루프 구조(도구명·계약 실제)
도구 6종: get_stock · get_price · get_order_status · search_knowledge_base · …
[구조 예시]  사용자 "재고 있어?"
  → LLM 판단: tool_call get_stock(product_id=…)
  → 관찰:     {"ok": true, "stock": 12}          (실패도 {"ok": false, "error": …} 로 통일)
  → LLM 응답: "재고 12개"     ← 실패 관측이면 루프가 인자 고쳐 재호출
안전장치: 중복 호출 서명 차단 · 문맥 trim(head+tail 짝) · TypeError→bad_arguments
배운 점 좋은 도구는 실패도 구조화된 관찰({"ok": false, ...})로 돌려줘야 루프가 스스로 고쳤다. 중복 호출·문맥 길이·잘못된 인자 같은 현실 문제를 안전장치로 다뤘다(function_calling_console·agent_loop·planning 실습). (자세히: Function Calling·ReAct)
다음으로 — 도구로 행동은 하되, LLM이 모르는 최신·전용 지식은 어떻게 줄까.

CH 04지식 — Vector DB와 RAG#

회수

0708엔 LLM에 외부 지식을 붙였다. 문서를 임베딩(9주차 Word2Vec의 확장 — 문장 임베딩 ko-sroberta)해 Vector DB(FAISS)에 넣고, 질문으로 유사 검색해 상위 문서를 프롬프트에 끼우는 RAG다. 이것이 커머스 에이전트에선 상품·정책 지식 검색 도구가 됐다.

_unified_mall_agent_project/app/rag — 실제 RAG 설정·동작
임베딩  jhgan/ko-sroberta-multitask (normalize=True)  ·  스토어 FAISS(save/load_local)
청킹    CHUNK_SIZE 400 · OVERLAP 50   |   검색 RAG_TOP_K 3 · RAG_MAX_DISTANCE 1.5
검증 예  질의 "ReAct 에이전트 무한루프 방지" → loop_safety.txt 1순위 (거리 작을수록 유사)
배운 점 9주차의 "의미가 좌표가 된다"가 여기서 실전이 됐다 — 임베딩 좌표의 거리로 관련 문서를 찾는다. FAISS의 거리(작을수록 유사)·정규화·거리 임계로 엉뚱한 검색을 막는 게 핵심이었다(rag_console·embedding_console·vector_db 실습). (자세히: Vector DB·RAG)
그래서 — 제어(프롬프트)·행동(도구)·지식(RAG)이 갖춰졌다. 마지막은 이 셋을 하나로 합치는 일이었다.

CH 05통합 — ReAct 커머스 에이전트#

회수

0709, 종착점. 형태소·임베딩·분류·BERT·트랜스포머·LLM·프롬프트·Function Calling·RAG를 하나의 쇼핑몰 에이전트(FastAPI)로 통합했다. 여섯 도구가 모두 같은 계약(dict)을 돌려주니, DB 조회·환율 계산·FAISS 검색을 한 ReAct 루프가 조합했고, 수동 경로와 LangChain 경로가 같은 도구·응답 스키마를 공유했다.

_unified_mall_agent_project — 통합 아키텍처(스테이지 → 모듈)
엔드포인트  /chat(수동 ReAct)  ·  /lc-chat(LangChain)  → 같은 6도구·AgentResponse 공유
도구 계약   get_stock·get_price·search_knowledge_base … 모두 {"ok": …} dict 반환(성공/실패 동일 형식)
스테이지    형태소→임베딩→분류→BERT→Transformer→LLM→프롬프트→FunctionCalling→RAG→ReAct 통합
검증        pytest 124 케이스 통과 (핵심 경로·실패 관측·라우터)
깨달음 한 학기의 조각들이 부품 → 통합으로 꿰였다. 각 스테이지 콘솔 실습이 부품이었고, 통합 프로젝트가 그 부품을 조립한 완성품이었다. "잘 쓰는 것"은 곧 여러 능력을 하나의 일관된 인터페이스로 합치는 설계였다. (자세히: 종합 — ReAct 커머스 에이전트)
그래서 — 11주차는 교과목3의 마침표이자, 조각들이 하나의 제품으로 모이는 순간이었다.

CH 06종합 회고#

잘한 점 / 부족했던 점 / 다음 한 수

  • 잘한 점 — 스테이지별 콘솔 실습으로 부품을 하나씩 익힌 뒤 통합 프로젝트로 합쳐, "왜 이 층이 필요한가"를 결핍(일관성·행동·지식)으로 설명할 수 있게 됐다.
  • 부족했던 점 — LLM API 실제 대화 로그를 글에 충분히 담지 못했다(구조·설계·측정값 중심). MCP·LangGraph는 자료 부족으로 다루지 못했다.
  • 다음 한 수 — 통합 에이전트의 실제 대화 세션(도구 호출 추적)을 캡처해 사례로 붙이고, MCP·LangGraph로 멀티 에이전트를 확장한다.
관통 교훈
  1. 프롬프트는 설계다. 역할·경계 예시·인젝션 방어·CoT — 부탁이 아니라 구조.
  2. 도구엔 계약이 필요하다. 성공·실패를 같은 형식(dict)으로 돌려줘야 ReAct 루프가 스스로 고친다.
  3. RAG는 임베딩의 실전이다. 9주차의 의미 좌표가 여기서 문서 검색이 됐다.
  4. 부품에서 통합으로. 잘 쓰는 것은 여러 능력을 하나의 일관된 인터페이스로 합치는 설계다.
